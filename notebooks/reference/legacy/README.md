# Старые ноутбуки и справочные наработки

## Назначение

Эта папка хранит старые исследовательские ноутбуки, прототипы и технические наработки проекта KOMUS.

Они нужны как справочный материал для:

- поиска уже реализованных решений;
- повторного использования удачных идей;
- изучения старых подходов к СПАРК, признакам, моделям и интерфейсу;
- дополнительного контекста для Developer / Codex.

Эти файлы не являются актуальным source of truth проекта.

## Главное правило

Старый код можно изучать, но нельзя автоматически переносить в текущую систему.

Перед повторным использованием необходимо проверить:

- датасет;
- target;
- identifier;
- признаки;
- preprocessing;
- split / folds / seed;
- final test;
- возможную утечку данных;
- временную корректность;
- соответствие текущей архитектуре KOMUS.

Старые метрики и выводы не заменяют accepted evidence текущего исследования.

## Актуальный source of truth

При конфликте приоритет имеют:

1. текущая задача;
2. подтверждённые требования заказчика;
3. docs/CURRENT_STATE.md;
4. принятые решения проекта;
5. accepted Stage 1–20;
6. проверенные artifacts из reports/;
7. текущий код;
8. legacy-материалы из этой папки.

## Структура

### spark_dataset_builder/

Старые разработки по сбору и подготовке данных из СПАРК.

Особенно полезны:

- выбор методов СПАРК API;
- выбор полей;
- группы признаков;
- выбор признаков галочками;
- расчётные и пользовательские признаки;
- workflow/config;
- тест одной компании;
- массовый сбор;
- checkpoint/resume;
- dataset fingerprint;
- разделение сырых ответов и ML-матрицы;
- паспорт датасета.

Старый СПАРК-конструктор рассматривается как источник полезных механизмов, а не как готовое приложение для прямого переноса.

### model_pipeline/

Старые ноутбуки сравнения моделей и экспериментальных конвейеров.

Особенно интересны:

- реестр моделей;
- единый запуск;
- выбор модели;
- расчёт метрик;
- сравнение результатов;
- конфигурация эксперимента;
- элементы пользовательского интерфейса.

### data_analysis/

Старые EDA и исследования структуры данных.

Могут использоваться для решений по:

- первичной диагностике нового датасета;
- пропускам;
- типам признаков;
- распределениям;
- дисбалансу target;
- группировке признаков;
- визуализации;
- контролю качества.

### other/

Другие старые исследования и прототипы, которые пока не относятся к одной из основных групп.

## Правило для Developer / Codex

Правильный порядок:

старое решение
→ понять назначение
→ проверить актуальность
→ выделить минимальный полезный механизм
→ реализовать в текущей архитектуре
→ проверить

Не следует копировать большие блоки старого notebook в новый проект без анализа.

## Текущее направление

Целевая логика проекта:

источник данных
→ готовый датасет
→ паспорт датасета
→ реестр и группы признаков
→ выбор признаков
→ выбор модели
→ контролируемый эксперимент
→ единый результат
→ понятный русскоязычный интерфейс

Legacy notebook помогают реализовать отдельные части этого процесса, но не определяют новую архитектуру целиком.
