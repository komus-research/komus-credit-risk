# Реализованные изменения в ветке `research/shap-llm-interpreter`

## Локальная настройка LLM через `.env`

Добавлена загрузка настроек внешнего интерпретатора из локального файла `.env` в корне проекта. Это позволяет включить безопасный режим `REDACTED_V1`, выбрать зарегистрированного провайдера и модель, а также передать `OPENAI_API_KEY` без ввода значений при каждом запуске Streamlit.

Локальный `.env` уже исключён из Git и содержит пустые поля для модели и ключа. Ключ пользователь заполняет самостоятельно на своём компьютере; он не должен передаваться в чат, документацию или коммиты. Добавлен отслеживаемый `.env.example` без секретов, показывающий обязательные имена переменных. Системные переменные окружения имеют приоритет над значениями из `.env`.

Изменённые файлы:

- `app/bootstrap.py` — перед созданием runtime загружает корневой `.env` через `python-dotenv`, если вызывающая сторона не передала отдельное окружение;
- `pyproject.toml` и `uv.lock` — добавлена и зафиксирована зависимость `python-dotenv`;
- `.env` — локальная конфигурация, исключённая из Git;
- `.env.example` — безопасный шаблон конфигурации без ключа;
- `tests/test_streamlit_bootstrap.py` — проверено, что полный набор настроек из временного `.env` переводит Result Interpreter в готовое состояние.

## Поддержка XLSX во всех пользовательских загрузках

Добавлен формат `.xlsx` наряду с существующими CSV и XLSB: для исходного датасета, файла с новыми ИНН и признаками, а также словаря описаний признаков. Это позволяет использовать обычную книгу Excel без предварительного преобразования в CSV или XLSB. Формат выгружаемых шаблонов и прогнозов не менялся — они остаются CSV.

Изменённые файлы:

- `app/streamlit_app.py` — XLSX доступен в трёх загрузчиках; обновлены подписи и сообщение о допустимых расширениях.
- `app/bootstrap.py` — разрешён XLSX при проверке локального источника.
- `src/komus_risk/data/tabular.py` — предварительный просмотр столбцов XLSX подключён к существующему чтению книг Excel.
- `app/upload_history.py` — файлы XLSX сохраняются в истории загрузок и восстанавливаются после обновления страницы.
- `app/feature_descriptions.py` — словарь XLSX читается через `openpyxl` с прежним точным сопоставлением имён признаков.
- `src/komus_risk/application/model_inference.py` — пакет новых ИНН в XLSX читается через `openpyxl` и проходит прежнюю проверку структуры и значений.
- `docs/BRANCH_RESEARCH_SHAP_LLM_INTERPRETER_ARCHITECTURE.md` — во всех трёх пользовательских потоках указан актуальный набор форматов.
- `tests/test_streamlit_bootstrap.py`, `tests/test_dataset_onboarding.py`, `tests/test_upload_history.py`, `tests/test_feature_descriptions.py`, `tests/test_model_versions.py` — добавлены проверки всех трёх путей загрузки и восстановления XLSX из истории.

Первый лист XLSX используется по умолчанию. При загрузке новых ИНН по-прежнему обязательны точные названия и значения всех признаков выбранной сохранённой модели; само расширение файла этих правил не меняет.

## Изменение 1. Выбор локального файла в Streamlit

### Цель задачи

Сделать выбор локального датасета в Streamlit понятным и контролируемым для пользователя.

До изменений интерфейс позволял вручную вводить произвольный путь к файлу. Это могло приводить к опечаткам, передаче некорректного пути и попыткам выбрать неподдерживаемый формат. Также системное окно выбора содержало возможность показать все типы файлов.

### Что было сделано

- Удалён ручной ввод пути к локальному файлу.
- Выбор файла реализован через штатный загрузчик Streamlit, который открывает Проводник из браузера.
- В интерфейсе явно указано, что разрешены форматы CSV и XLSB.
- Загрузчик ограничен файлами `.csv` и `.xlsb`.
- Добавлена повторная проверка расширения после выбора файла.
- Для неподдерживаемого расширения добавлено понятное пользовательское сообщение.
- Ограничение CSV/XLSB добавлено также на уровне разрешения источника данных, чтобы его нельзя было обойти через внутренний вызов.
- Сохранено отображение имени выбранного файла и его статуса перед проверкой источника.
- Сохранена возможность заменить ранее выбранный файл.

### Зачем это было сделано

- Чтобы пользователь не вводил файловый путь вручную.
- Чтобы исключить ошибки и неоднозначность при заполнении поля.
- Чтобы выбор происходил через Проводник Windows и не зависел от запуска GUI-окна внутри серверного потока Streamlit.
- Чтобы приложение принимало только согласованные форматы данных.
- Чтобы неподдерживаемый файл отклонялся до запуска чтения или подготовки датасета.
- Чтобы одно и то же ограничение действовало как в интерфейсе, так и во внутренней логике приложения.

### Изменённые файлы

#### `app/streamlit_app.py`

- Удалены элементы интерфейса для ручного ввода пути.
- Обновлён текст блока выбора локального файла.
- Зафиксирован список допустимых расширений: CSV и XLSB.
- Добавлена обработка выбора файла с неподдерживаемым расширением.
- Обновлена логика хранения и восстановления выбранного файла в состоянии Streamlit.

#### `app/local_file_picker.py`

- Добавлено безопасное сохранение выбранного в браузере файла в служебном каталоге приложения.
- Добавлена проверка расширения загруженного файла.
- Добавлен отдельный тип ошибки для неподдерживаемого расширения.
- Имя файла очищается от элементов пути, а сохранённая копия получает идентификатор содержимого.

#### `app/bootstrap.py`

- Список форматов локального источника ограничен CSV и XLSB.
- Внутренняя проверка источника теперь отклоняет остальные расширения независимо от интерфейса.

#### `tests/test_streamlit_bootstrap.py`

- Обновлена проверка интерфейса с учётом удаления ручного пути.
- Добавлена проверка фильтра форматов в браузерном загрузчике.
- Добавлена проверка успешного выбора разрешённого формата.
- Добавлена проверка отклонения неподдерживаемого расширения.
- Добавлена проверка ограничения форматов на уровне источника данных.

### Проверка результата

- Целевые тесты новой логики успешно проходят.
- Проверено, что Streamlit продолжает отвечать после изменений.
- Проверено отсутствие ошибок форматирования в итоговом Git diff.
- Тест, прежде требовавший локальный `data/raw/Data_final.xlsb`, переведён на временный тестовый файл; полный набор тестов теперь не зависит от наличия большого исторического файла на компьютере разработчика.

### Ограничения текущего этапа

Выбор файла формата CSV или XLSB подтверждает только допустимый физический формат. Произвольный новый датасет не становится автоматически готовым к ML-эксперименту: для него по-прежнему необходимы проверка структуры, определение целевой колонки, реестр признаков и подготовка evaluation population.

## Изменение 2. Отдельный экран SHAP

### Цель задачи

Сделать уже рассчитанные объяснения моделей видимыми в Streamlit, не смешивая их с метриками и не выдавая старые объяснения за результат произвольного нового запуска.

### Что было сделано

- Добавлен шестой экран «SHAP» после экрана результата и переход к нему.
- Подключены опубликованные результаты исследования Stage 2 без повторного обучения моделей и расчёта SHAP.
- Для CatBoost, XGBoost и LightGBM показаны диаграмма и таблица глобальной важности признаков.
- Для ансамбля GBDT_mean показан общий рейтинг трёх моделей с явным пояснением, что отдельный SHAP ансамбля не рассчитывался.
- Добавлены три сохранённых локальных примера XGBoost со значениями признаков, направлениями и величинами SHAP-вкладов.
- Добавлена проверка соответствия текущего запуска историческому протоколу по датасету, модели, набору признаков, seed и числу фолдов.
- Добавлены пояснения, что SHAP не является причинной оценкой и его величины нельзя читать как проценты изменения вероятности.

### Зачем это было сделано

Пользователь может увидеть фактические результаты уже проведённого исследования в интерфейсе. При этом экран честно различает исторические SHAP-артефакты и текущий эксперимент: для нового набора признаков или другого протокола SHAP пока не рассчитывается автоматически.

### Изменённые файлы

- `app/streamlit_app.py` — экран SHAP, визуализация и навигация.
- `app/shap_evidence.py` — загрузка сохранённых данных и проверка сопоставимости.
- `app/session_state.py` — поддержка шестого шага мастера.
- `tests/test_shap_evidence.py`, `tests/test_streamlit_session_state.py`, `tests/test_streamlit_bootstrap.py` — проверки данных, сопоставимости и навигации.

### Ограничение

Показанные SHAP-значения рассчитаны в Stage 2. Для SHAP каждого нового эксперимента потребуется отдельный расчёт и сохранение объяснений во время обучения моделей.

## Изменение 4. История загрузок и ускорение повторной проверки

На этом этапе на экране выбора локального файла добавлен список недавно загруженных CSV и XLSB. Из него можно снова выбрать файл без повторной передачи через браузер. Первоначально история относилась только к текущей сессии и содержала до десяти файлов; сохранение истории между перезагрузками добавлено позже в изменении 8. Сами загрузки остаются в локальном каталоге служебных данных приложения. Файл сохраняется при изменении загрузчика, а не при каждой перерисовке страницы. Для двух последних проверенных файлов повторно используется подготовленный результат, если размер и время изменения файла не поменялись. Это ограничение не даёт истории занимать слишком много оперативной памяти. Кнопка «Проверить повторно» по-прежнему выполняет полную проверку. При выборе другого источника прежний подготовленный контекст сбрасывается, чтобы его результат не показывался как результат нового файла.

Это ускоряет повторное использование файлов, но первая проверка нового файла и подготовка произвольного датасета по-прежнему не ускорены. Произвольный CSV/XLSB без принятого исторического профиля пока нельзя использовать для обучения модели.

Изменённые файлы: `app/streamlit_app.py` — интерфейс истории, обработка загрузки и повторное использование проверки; `tests/test_streamlit_bootstrap.py` — проверки истории и кеша.

Уточнение интерфейса: список истории не появляется сразу после загрузки нового файла. Он становится виден после перехода с вкладки «Данные» на вкладку «Признаки» и возвращения назад. Позже добавлено также отображение восстановленной истории после перезагрузки страницы; это позволяет вернуть новый датасет, для которого переход к «Признакам» пока заблокирован.

## Этап 2. Анализ и подтверждение нового датасета — выполнен как подготовка

**Что изменилось для пользователя.** Кнопка «Изучить данные и предложить роли» запускает полное чтение файла и последовательность `TabularReader → DatasetInspector → DatasetPreparationAnalyzer`. Экран отдельно показывает факты о таблице (число строк, типы, пропуски, уникальные значения) и предложения системы (цель, идентификатор, предупреждения). Предложения не принимаются автоматически: пользователь выбирает целевую колонку, значение события, идентификатор и разрешённые признаки, затем нажимает «Подтвердить подготовку».

**Что проверяет backend.** Анализ и подтверждение должны относиться к одной версии файла; цель должна быть бинарной, без пропусков и с минимум двумя строками каждого класса; идентификатор — непустым и уникальным. Цель и идентификатор нельзя включить в признаки. Разрешаются только числовые/булевы признаки без пропусков и бесконечных значений; столбцы с предупреждением о возможной утечке цели блокируются. При смене файла прежний анализ и подтверждение сбрасываются.

**Что получается на выходе.** Создаются `DatasetContract`, `FeatureRegistry` и `EvaluationPopulation` для строк именно нового файла. Отпечаток подтверждённой конфигурации учитывает файл и выбранные роли/признаки, поэтому два набора признаков не смешиваются. Популяция пока содержит все строки и не является обучающей/проверочной выборкой. Объекты хранятся только в сессии Streamlit и не подменяют исторический `dataset_context`; паспорт имеет статус `confirmed_pending_protocol`. Новая модель не обучается, Gini не вычисляется, файл модели не сохраняется.

**Зачем.** Отделить проверенную структуру и подтверждённые человеком роли от ещё не утверждённого протокола обучения; не применять индексы исторического Stage 3 к новому файлу.

## Изменение 8. История загрузок после перезагрузки страницы

Раньше список последних файлов и признак его видимости жили только в памяти сессии Streamlit. Обновление страницы могло создать новую сессию: каталог с загруженными CSV/XLSB оставался на диске, но список исчезал. Для локального прототипа добавлен отдельный реестр последних десяти загрузок в `.streamlit-artifacts/upload-history/`. Реестр привязан к случайному идентификатору в параметре адреса страницы, а не является общим списком всех файлов на сервере. При повторном открытии того же адреса проверяются существование, размер и допустимое расположение файлов, после чего список восстанавливается. Уже открытая сессия со старой историей переносит её в новый реестр без преждевременного показа. В реестре не хранятся произвольные абсолютные пути.

Сразу после новой загрузки история по-прежнему скрыта. После обновления страницы сохранённые записи видны также для нового датасета, которому текущий мастер пока не позволяет перейти к «Признакам». Выбор записи не восстанавливает прежний ML-контекст или кеш анализа: пользователь снова нажимает «Проверить источник». История сохраняет ссылку на файл, но не обученную модель и не результаты эксперимента.

Изменения по файлам: новый `app/upload_history.py` — идентификатор, проверка и атомарное хранение ограниченного реестра; `app/streamlit_app.py` — загрузка истории при старте, запись при выборе файла и сохранение только безопасного имени файла; новый `tests/test_upload_history.py` — сохранение между сессиями, разделение по идентификаторам и отбрасывание отсутствующих/посторонних файлов; `tests/test_streamlit_bootstrap.py` — проверка записи при загрузке. Архитектурный документ дополнен границами локального хранения.

Ограничения: прежние загрузки из уже потерянной сессии нельзя безопасно автоматически приписать конкретному браузеру — их нужно выбрать через Upload ещё один раз. Идентификатор находится в URL: скопированная ссылка откроет ту же историю, поэтому ссылку нельзя передавать посторонним. Для публичного многопользовательского сервиса требуются настоящая аутентификация и права доступа; этот механизм их не заменяет. Потеря адреса с идентификатором или удаление каталога `.streamlit-artifacts` также лишит доступа к истории. Проверка после изменения: `python -m unittest discover -s tests -q` — 166 тестов прошли.

## Этап 3. Оценка конфигурации нового датасета — выполнена для нетемпоральных данных

После подтверждения ролей пользователь отдельно подтверждает, что каждая строка соответствует одному ИНН и в файле нет временной последовательности наблюдений. Backend проверяет это решение, статус подготовленного датасета, полную популяцию именно нового файла, неизменность исходного файла и минимум 60 строк с не менее чем 30 наблюдениями каждого класса для OOF и внутренней проверки бустинга. Файлы с явными столбцами года, даты или периода блокируются: текущая случайная OOF-проверка не предназначена для оценки прогноза будущих периодов. Для скрытой временной структуры остаётся обязательным осмысленное подтверждение пользователя; автоматический поиск названий столбцов не даёт гарантии.

После успешного подтверждения открывается существующий мастер: выбор подмножества заранее разрешённых признаков, выбор CatBoost/XGBoost/LightGBM/GBDT_mean, затем настройка seed и числа фолдов, построение плана и запуск. Цель, ИНН и заблокированные proxy-поля не становятся признаками. Runner работает со строками нового файла, а не с историческими индексами Stage 3; результаты и OOF-прогнозы сохраняются в существующем хранилище артефактов экспериментов. В плане показывается стабильный ID конфигурации, зависящий от датасета, популяции, признаков, модели и протокола.

Важно: анализ ролей на этапе 2 уже использовал весь файл. Поэтому для нового датасета **нет независимой закрытой финальной выборки**; Gini и другие OOF-метрики обозначены как исследовательские. Этот этап не создаёт одну итоговую модель для новых ИНН и не сохраняет её: это остаётся этапом 4. Файлы с повторными ИНН и временные данные требуют отдельного группового/временного протокола, который пока не реализован.

## Этап 4. Итоговое обучение и версии моделей — выполнен

После успешного OOF-эксперимента на экране результата добавлено отдельное действие «Обучить и сохранить модель». Оно повторно обучает выбранный алгоритм с теми же признаками и зафиксированным профилем на разрешённой обучающей популяции: для `Data_final` только на working-части, для нового подтверждённого датасета — на его размеченных строках. Закрытая контрольная выборка не используется. Перед обучением проверяются сохранённый артефакт оценки, совпадение датасета, популяции, реестра признаков, версии кода и неизменность исходного файла. OOF-артефакт с метриками остаётся отдельным от обученной модели.

Каждое обучение создаёт новую неизменяемую версию в `.streamlit-artifacts/models/<id>/`. Сохраняются нативные файлы CatBoost, XGBoost, LightGBM или три файла для GBDT_mean; Python pickle/joblib не применяется. Паспорт версии связывает её с исходным файлом, датасетом, OOF-артефактом, популяцией, целью, положительным классом, упорядоченными признаками и типами, профилем модели, seed, версиями кода и библиотек. Манифест содержит SHA-256 файлов. Перед публикацией проверяется чтение нативной модели; при последующей загрузке проверяются целостность и совместимость среды. Повреждённая запись не попадает в список пригодных версий. Даже одинаковая конфигурация при новом обучении получает новый ID; разные датасеты и наборы признаков не смешиваются.

На первом экране появился каталог сохранённых версий, считываемый с диска после перезагрузки страницы. Он показывает дату, датасет, алгоритм, количество признаков и связанный OOF-результат. После установки этого этапа уже запущенный сервер Streamlit следует один раз перезапустить: прежний runtime может оставаться в памяти; при обнаружении такого состояния интерфейс покажет понятное сообщение вместо падения. Пользователь пока не может загрузить файл без метки для пакетного прогноза: это этап 5. Экран SHAP для нового обученного артефакта пока не рассчитывается: это этап 6. Контрольные суммы обнаруживают случайное повреждение, но не заменяют права доступа или цифровую подпись. Каталог локален для компьютера, на котором работает Streamlit, и требует резервного копирования для долговременного хранения.

## Этап 5. Использование сохранённой модели — базовый пакетный прогноз

Каталог моделей на экране данных теперь интерактивный: выбор строки открывает отдельную вкладку «Прогноз» именно с этой версией. После перезагрузки страницы каталог по-прежнему считывается с диска; версию можно выбрать повторно. На экране прогноза показываются алгоритм, датасет, ID версии и **точные сохранённые имена признаков** с описаниями. Доступен пустой CSV-шаблон со столбцом ИНН и всеми обязательными признаками.

Пользователь загружает CSV или XLSB с одним или несколькими ИНН и нужными значениями признаков. Backend восстанавливает сохранённую нативную модель, проверяя паспорт, контрольные суммы и совместимость библиотек; повторное обучение не происходит. До прогноза проверяются формат, размер, число строк, наличие точных имён столбцов, уникальные ИНН из 10 или 12 цифр и конечные числовые значения каждого обязательного признака. При похожем написании с буквами русского/английского алфавита интерфейс сообщает возможную опечатку, но не исправляет заголовок сам. Дополнительные столбцы, включая фактическую метку, игнорируются с предупреждением. При ошибке любого обязательного значения пакет не прогнозируется частично: пользователь исправляет файл и загружает его заново.

Результат — таблица ИНН, вероятности события и классификации при техническом пороге 0,5; её можно скачать как CSV. Порог не утверждён как бизнес-правило. Эти значения — прогноз модели, а не известный факт дефолта. Результат хранится только в текущей сессии Streamlit, не записывается в каталог моделей и не содержит SHAP: индивидуальное объяснение остаётся задачей этапа 6. Сохранённая модель требует **все** свои признаки; один только ИНН для прогноза недостаточен. Ограничение текущего пути — до 100 000 строк и 200 МБ на файл. Для CSV используется UTF-8; автоматического исправления названий, заполнения пропусков и пересчёта признаков нет.

## Этап 6. Local SHAP → LLM для CatBoost, XGBoost и LightGBM

Индивидуальное объяснение сохранённой модели расширено с CatBoost на XGBoost и LightGBM через существующий общий прикладной контракт. Отдельные ветки в Streamlit не добавлялись: интерфейс по-прежнему вызывает `IntegrationWorkflowService`, а composition root регистрирует один `LocalExplanationService` для трёх поддержанных семейств.

После восстановления нативного файла XGBoost использует `Booster.predict(..., pred_contribs=True)` и `output_margin=True`, LightGBM — `Booster.predict(..., pred_contrib=True)` и `raw_score=True`. Для каждой выбранной строки проверяются точный порядок признаков, совпадение повторно рассчитанной вероятности с показанной в таблице, аддитивность `base value + сумма SHAP = raw margin` и соответствие сигмоиды raw margin вероятности. CatBoost использует прежний нативный механизм; его совместимый метод сохранён.

Далее доказательство передаётся в существующую модель-независимую LLM-цепочку. `REDACTED_V1` не изменён: наружу не выходят ИНН, `row_id`, исходные значения признаков, `base_value`, raw margin и полная provenance-информация. Вероятность рассчитывается моделью до LLM и не может быть заменена текстовым интерпретатором.

### Почему `GBDT Mean` не включён

`GBDT Mean` усредняет три вероятности, тогда как нативные TreeSHAP-вклады каждого компонента аддитивны в его собственном пространстве raw margin. Среднее raw-margin SHAP не объясняет среднее вероятностей и может дать математически неверный результат, поэтому ансамбль не зарегистрирован для локального объяснения и интерфейс честно возвращает `UNSUPPORTED`.

Безопасное дальнейшее расширение требует нового явно версионированного контракта. Предпочтительный вариант — передавать финальную среднюю вероятность и три отдельные компонентные SHAP-сводки, каждая из которых связана со своей компонентной вероятностью; объединять их в один псевдо-SHAP запрещено. Альтернатива — отдельный probability-space explainer для ансамбля с зафиксированным фоновым распределением, проверкой точности, производительности и privacy boundary. До такого решения реализация наугад не добавлялась.

### Проверка четырёх LLM-ролей

На синтетическом обезличенном payload выполнены реальные запросы для менеджера по продажам, кредитного контролёра, юриста и специалиста ИБ. Первая проверка обнаружила качественный ярлык «повышенная вероятность» без утверждённого порога. Общий системный промпт усилен запретом на категории высокой/низкой/приемлемой вероятности без явно переданного порога; повторный прогон прошёл критерии фактической точности, отсутствия причинности и бизнес-решений, корректной обработки неизвестного смысла признака и ролевого различия. Примеры, токены и расчёт стоимости записаны в [отдельном отчёте](BRANCH_RESEARCH_SHAP_LLM_INTERPRETER_ROLE_EVALUATION.md).
