# Контекст проекта

## Статус документа

Актуальная точка входа в проект. Обновляется после завершения значимого исследовательского этапа, изменения требований заказчика или смены source of truth.

Дата фиксации: **2026-08-19**.

## 1. Проект

**Заказчик:** ООО «Комус».

**Направление:** исследование применимости современных DS/ML/LLM-подходов для прогнозирования дефолта коммерческих организаций РФ на горизонте 1 года.

Главная задача — не просто повторить существующий скоринг Комуса, а исследовать модели, признаки и подходы, понять источник качества и ограничения, а затем превратить исследовательскую ML-логику в экспериментальный инструмент сравнения моделей и настроек.

Локальный репозиторий клонирован в `D:\Projects\komus-credit-risk`. Перед созданием окружения проверено: активная ветка `main`, `origin` указывает на `https://github.com/alekseeva943-cloud/komus-credit-risk.git`, рабочее дерево было чистым и синхронизированным с `origin/main`.

Python 3.12.2 выбран осознанно, а не случайно. Historical baseline №06 уже использует современный ML-стек, в котором сохранены версии XGBoost и SHAP, требующие более нового Python, чем 3.10. Основная исследовательская среда не должна искусственно ограничивать актуальные ML-библиотеки и будущие современные модели только ради старой строки в ТЗ.

При этом требование исходного ТЗ о воспроизводимости на **Python 3.10** не игнорируется. Оно сохраняется как отдельный **delivery compatibility gate**: перед поставкой необходимо явно проверить, можно ли запустить текущую систему на Python 3.10 с совместимым набором зафиксированных зависимостей без изменения ML-логики. Если это возможно — формируется отдельный совместимый lock/container. Если нет — несовместимость должна быть подтверждена воспроизводимым техническим тестом и вынесена на согласование заказчику.

Код проекта по возможности пишется без ненужной зависимости от синтаксиса/возможностей только Python 3.12, чтобы не создавать искусственных препятствий для такой проверки.

Docker учитывается как будущий механизм воспроизводимой передачи и offline/deployment-упаковки, но не вводится до стабилизации ML-core и runtime contracts.

Colab остаётся дополнительной средой для демонстраций, обмена или отдельных запусков, но больше не является source of truth для текущего кода.

## 4. Протокол baseline v1

Зафиксированная конфигурация полного прогона:

- seed: `42`;

- seed stability: `7, 17, 42, 101, 2026`;
- SHAP: включён;
- Optuna: включена, 30 trials для подбора сильных моделей.

Final test использовался только после фиксации кандидатов и не должен использоваться для повторного выбора модели, признаков, гиперпараметров или threshold.

## 5. Основные результаты baseline v1

На сопоставимой базовой OOF/CV-процедуре:

- CatBoost: Gini ≈ **0.9236**, PR-AUC ≈ **0.8664**;
- XGBoost: Gini ≈ **0.9232**, PR-AUC ≈ **0.8658**;
- LightGBM: Gini ≈ **0.9228**, PR-AUC ≈ **0.8655**.

Вывод: победил **класс градиентных бустингов**, а не один абсолютный алгоритм. Различия между лидерами измеряются тысячными.

После Optuna прирост остался небольшим. Для XGBoost Gini вырос примерно до **0.9244**. Class weights не дали значимого улучшения ранжирования и ухудшили часть операционных метрик.

При threshold ≈ `0.5` Recall дефолтного класса находился около **0.69** при Precision около **0.91–0.92**. Снижение threshold повышает Recall, но резко увеличивает FP.

## 6. Критический результат абляций

Исторический эксперимент показал:

- все 49 признаков: Gini ≈ **0.9244**;
- без `Q_B1_norm`: ≈ **0.9183**;
- без `Q_B2_norm`: ≈ **0.9172**;
- без обоих: ≈ **0.8070**.

`0.8070` — результат диагностической абляции старой схемы, а **не новый честно построенный baseline без двух индексов**.

## 7. Актуальные ответы заказчика после baseline v1

### `Q_B1_norm`

Индекс финансового риска СПАРК (ИФР). Был доступен до дефолта, но **не должен использоваться в финальной рабочей модели**. Разрешён только как технический ориентир и для проверки механики.

### `Q_B2_norm`

Индекс должной осмотрительности СПАРК (ИДО), рассчитываемый СПАРК на основе подходов/разъяснений ФНС. Был доступен до дефолта, но **не должен использоваться в финальной рабочей модели**. Разрешён только как ориентир.

Следствие: старые кандидаты notebook №06, содержащие `Q_B1_norm` и/или `Q_B2_norm`, остаются историческими результатами, но не являются актуальными production-кандидатами.

## 8. Target и временное ограничение

`DefMark` сформирован **вручную экспертами Комуса** на основе внутреннего бизнес-понимания дефолта и исторических фактов за длительный период 2005–2024.

Для бизнеса дефолт — прежде всего прекращение исполнения обязательств/фактическая неплатёжеспособность, а не только формальное юридическое банкротство.

В текущем `Data_final.xlsb` **нет row-level даты наблюдения**, поэтому корректный temporal holdout восстановить нельзя.

Следовательно:

- random split/CV показывает внутреннюю способность обобщаться на другие компании;
- bootstrap и seed stability показывают устойчивость к случайным вариациям;
- эти проверки **не доказывают устойчивость на будущем периоде**.

Для будущего pipeline заказчик указал дату оценки **1 июня года, следующего за отчётным**, с возможным развитием к поквартальной настройке.

## 9. Текущая исследовательская задача

Первый вопрос новой итерации:

> Какой честный уровень качества достигают CatBoost, XGBoost и LightGBM на одном и том же допустимом наборе признаков после полного исключения `Q_B1_norm` и `Q_B2_norm`?

Первый эксперимент не должен одновременно менять feature engineering, threshold, class weights и tuning. Сначала нужен новый baseline на допустимом feature set.

Минимальные метрики:

- Gini;
- ROC-AUC;
- PR-AUC;
- Precision;
- Recall;
- F1;
- confusion matrix;
- CPU train time;
- CPU inference time;
- размер модели/ресурсные показатели по мере готовности общего runner.

## 10. CPU как часть постановки

Заказчик отдельно требует реалистичную работу на CPU.

Из актуальных ответов:

- обучение модели — ориентир **не более 8 часов**;
- прогноз одной компании — **не более 2 минут**.

Поэтому CPU runtime является обязательной осью сравнения, а не второстепенной технической деталью.

## 11. Интерпретируемость

Интерпретируемость — один из центральных критериев проекта.

Для DS-моделей требуется как минимум:

- глобальная важность;
- локальное объяснение прогноза;
- SHAP для поддерживаемых моделей;
- ясное различие между «влиянием на прогноз модели» и причинным влиянием на дефолт.

SHAP, permutation importance и абляции в baseline согласованно показали сильную зависимость модели от `Q_B1_norm` и `Q_B2_norm`.

## 12. Роль LLM

Текущее решение проекта: LLM не используется как кредитный predictor и не принимает решение о дефолте.

LLM используется **после ML-расчёта** как интерпретатор структурированных результатов:

- метрик;
- сравнений моделей;
- threshold-сценариев;
- SHAP/importance;
- ограничений исследования;
- актуальных бизнес-правил.

Внешний LLM API и допустимые локальные модели остаются отдельными открытыми вопросами заказчику. Архитектура не должна связывать ML-core с конкретным LLM-провайдером.

## 13. Бизнес-сценарий ошибок

Заказчик считает критичными и FP, и FN. Точное утверждённое денежное соотношение пока не получено.

Поэтому стоимость ошибок не зашивается в код. В будущем пользователь должен иметь возможность задать:

- реальные стоимости `C_FN` и `C_FP`; или
- только относительное соотношение `C_FN : C_FP`.

На их основе можно пересчитывать threshold-сценарии без переобучения модели.

Отдельно должна поддерживаться настраиваемая ёмкость ручной проверки. Заказчик сообщил ориентир: **30 минут ручной оценки одного ИНН**, а перебор порядка 100 000 клиентов хотя бы раз в квартал является практически тяжёлой задачей.

## 14. Направление будущего продукта

Приоритет заказчика — **исследовательский интерфейс сравнения моделей**. Рабочий интерфейс кредитного менеджера является следующей/опциональной частью.

Целевая эволюция:

`notebooks → reusable ML/data logic → ExperimentRunner → backend → frontend`

ML-логика не должна копироваться между notebook, API и UI.

## 15. Хранение и аудит

Заказчик указал ориентиры:

- данные для перемоделирования и история — горизонт около **3 лет**;
- история прогнозов вероятности дефолта — около **5 лет**.

Это будущие требования к архитектуре хранения. На текущем этапе они не являются причиной преждевременно вводить production-БД.

## 16. Открытые вопросы

1. Утверждённое отношение/стоимость FN и FP.
2. Допустимые локальные LLM и разрешение/запрет внешнего LLM API для обезличенных результатов.
3. В сообщении заказчика упоминаются «7 внешних признаков 100% дефолта», но перечислено 6; в разобранном инструменте внешними являются D1–D5 и D8, а D6–D7 внутренние. До уточнения не додумывать седьмой внешний фактор.
4. Temporal validation для текущего `Data_final` невозможна без дополнительной исторической структуры.

## 17. Source of truth

Приоритет при расхождении:

1. текущая явная инструкция пользователя;
2. свежие подтверждённые ответы заказчика;
3. актуальное ТЗ;
4. текущий GitHub-репозиторий и реальные файлы;
5. проверенные артефакты экспериментов;
6. архитектурные документы;
7. предыдущие чаты и summaries только как контекст.

Исторический baseline не переписывается под новые требования: новые требования фиксируются отдельно и проверяются новым экспериментом.
