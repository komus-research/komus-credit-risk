# Бизнес-правила

## Статус

Актуальные подтверждённые требования и ограничения заказчика для исследования и будущего инструмента.

Правило: **неопределённые бизнес-параметры не додумываются разработчиком и не зашиваются в код.** Если правило не подтверждено, оно хранится как open question или исследовательский сценарий.

Дата актуализации: **2026-08-19**.

## 1. Горизонт прогноза

Модель оценивает вероятность дефолта на горизонте **1 год**.

Смысл прогноза: если компанию оценивают на некоторую дату `T`, вероятность относится к событию дефолта на горизонте до `T + 1 год`.

## 2. Target `DefMark`

В текущем `Data_final.xlsb` target — `DefMark` (`0/1`).

Метки собирались за длительный период **2005–2024** и формировались **вручную экспертами Комуса** на основе внутреннего бизнес-понимания фактического дефолта.

Для Комуса дефолт не сводится только к юридическому банкротству. Существенен фактический отказ/прекращение исполнения платёжных обязательств и другие внутренние признаки неплатёжеспособности.

Следствие: `DefMark` — экспертная бизнес-разметка, а не полностью воспроизводимая формула из внешних реестров.

## 3. Внешние события «100% дефолта»

В переданных материалах перечислены внешние события, доступные через СПАРК/реестровые источники:

1. подача заявления в суд о банкротстве;
2. признание должника банкротом;
3. ввод процедур банкротства (наблюдение, внешнее управление, оздоровление);
4. принудительная ликвидация/исключение из ЕГРЮЛ/ИП по соответствующему основанию;
5. отзыв лицензии на осуществление деятельности;
6. прекращение исполнительного производства из-за отсутствия имущества либо невозможности установить его местонахождение.

Есть несогласованность источника: текст заказчика говорит о **7 внешних признаках**, но фактически перечисляет 6. В разобранном Excel-инструменте Комуса внешним набором соответствуют D1–D5 и D8; D6 и D7 являются внутренними событиями Комуса.

**До отдельного ответа заказчика седьмой внешний фактор не придумывать.**

## 4. Дата наблюдения и временная проверка

В текущем `Data_final.xlsb` нет отдельной достоверной row-level даты наблюдения, на которую были сформированы признаки каждой строки.

Данные исторически собирались за период 2005–2024, но по текущему файлу нельзя восстановить честный temporal holdout.

Поэтому:

- random split/CV разрешён как внутренняя оценка обобщения на другие компании;
- seed stability/bootstrap разрешены как stability checks;
- эти проверки **не считаются доказательством временной устойчивости на будущем периоде**.

Для будущего data pipeline заказчик указал базовую дату оценки: **1 июня года, следующего за отчётным**. В дальнейшем дата может стать настраиваемой поквартально.

## 5. Пропуски и нули из СПАРК

Неравномерная полнота данных у разных компаний является нормальной особенностью СПАРК и не должна автоматически трактоваться как ошибка выгрузки.

Нельзя без отдельной диагностики считать, что любой `0` или пустое значение означает отсутствие экономического события.

## 6. `Q_B1_norm` — ИФР СПАРК

`Q_B1_norm` — Индекс финансового риска СПАРК.

Подтверждено заказчиком:

- это готовый внешний индекс СПАРК; внутренняя формула/состав расчёта СПАРКом не раскрывается;
- индекс был доступен до наступления дефолта;
- сам факт использования не доказывает temporal leakage;
- индекс обладает сильным предсказательным сигналом;
- по внутренней оценке заказчика standalone Gini ИФР — **больше 0.80**;
- **в финальной рабочей модели использовать нельзя**;
- разрешено использовать только как reference/технический ориентир и для проверки механики экспериментов.

Смысловая интерпретация заказчика: ИФР отражает, насколько компания финансово рискованная.

## 7. `Q_B2_norm` — ИДО СПАРК

`Q_B2_norm` — Индекс должной осмотрительности СПАРК.

Подтверждено заказчиком:

- это готовый внешний индекс СПАРК; внутренняя формула/состав расчёта СПАРКом не раскрывается;
- рассчитывается СПАРК на основе собственных правил с опорой на подходы/разъяснения ФНС;
- был доступен до наступления дефолта;
- по внутренней оценке заказчика standalone Gini ИДО — **больше 0.67**;
- **в финальной рабочей модели использовать нельзя**;
- разрешён только как reference/технический ориентир;
- по информации заказчика показатель не прошёл внутренний корреляционный анализ для итогового набора факторов.

Смысловая интерпретация заказчика: ИДО отражает, насколько компании в целом можно доверять с точки зрения должной осмотрительности.

## 8. Запрещённый feature set и связь двух индексов

Для актуального рабочего кандидата запрещено использовать:

- `Q_B1_norm`;
- `Q_B2_norm`.

Система должна защищать это правило на уровне конфигурации feature set, а не полагаться только на внимательность пользователя.

Исторические/reference-эксперименты с этими признаками могут сохраняться и сравниваться, но должны быть явно маркированы как **reference only / not eligible for final working model**.

По информации заказчика, `Q_B1` и `Q_B2` сильно коррелированы между собой — ориентир около **0.83**. Поэтому удаление только одного индекса может почти не снижать качество: второй сохраняет значительную часть того же сигнала. Удаление обоих одновременно убирает большой информационный блок.

Это объяснение является бизнес-/экспертной информацией заказчика и не заменяет отдельную проверку корреляции и controlled ablation на фактическом dataset.

## 9. Recall ≈ 69% — рабочий ориентир

Заказчик подтвердил, что Recall порядка **69%** на текущем стандартном режиме является рабочим уровнем.

Следствие:

- задача не состоит в повышении Recall любой ценой;
- снижение threshold само по себе не считается улучшением качества модели;
- основное направление улучшения — новые допустимые факторы/признаки и новые подходы при контролируемом сравнении.

Заказчик отдельно приводит пример нового фактора: **статус системообразующего предприятия** может снижать вероятность дефолта. Это пример гипотезы, а не готовое бизнес-правило или заранее доказанный признак.

## 10. Threshold

Threshold — **бизнес-настройка поверх вероятностного прогноза**, а не неизменяемая часть модели.

Пользователь должен иметь возможность менять threshold без переобучения.

Каждый threshold-сценарий должен показывать как минимум:

- Recall;
- Precision;
- F1;
- FP;
- FN;
- число компаний, попадающих в риск/ручную проверку;
- при наличии утверждённой cost policy — стоимость ошибок.

## 11. Бизнес-цель через ПДЗ

Заказчик описывает бизнес-смысл проекта через снижение **ПДЗ — просроченной дебиторской задолженности**.

Текущий бизнес-ориентир: снизить ПДЗ примерно с **15% до 10%** по компаниям. По словам заказчика, в денежном выражении речь идёт о **сотнях миллионов**, поэтому даже несколько процентных пунктов имеют существенный бизнес-эффект.

При этом пока **нет подтверждённой формулы**, связывающей конкретные FN/FP, Recall, threshold или Gini с изменением ПДЗ на определённое число процентных пунктов.

Следствие: цель `15% → 10%` фиксируется как бизнес-KPI/контекст, но не превращается разработчиком по догадке в cost function или acceptance threshold.

## 12. Стоимость ошибок FN/FP

Заказчик считает важными **оба типа ошибок**: FP и FN.

Точное утверждённое соотношение стоимости пока не получено.

Поэтому:

- `C_FN` и `C_FP` **не фиксируются в коде**;
- значения `5` и `1`, использованные в историческом notebook для функции `5×FN + 1×FP`, являются только исследовательским примером;
- frontend должен позволять задавать реальные денежные стоимости либо относительное соотношение;
- до подтверждения бизнеса расчёт называется **исследовательским cost scenario**, а не оптимальным бизнес-порогом.

Базовая функция сценария:

`Cost = C_FN × FN + C_FP × FP`

Если важен только выбор threshold, абсолютный масштаб стоимости может быть заменён отношением `C_FN : C_FP`.

## 13. Ёмкость ручной проверки

Заказчик сообщил ориентир: **около 30 минут на ручную оценку одного ИНН**.

Для масштаба порядка **100 000 клиентов** один полный ручной проход составляет примерно **50 000 человеко-часов** (`100 000 × 0.5 часа`). По словам заказчика, пересматривать базу требуется хотя бы примерно раз в квартал, поэтому полный ручной процесс практически не масштабируется.

Поэтому ёмкость ручной проверки является отдельной настраиваемой business policy:

- лимит компаний на период — не фиксирован;
- среднее время на одну проверку — настраиваемо;
- период — настраиваем;
- будущий интерфейс должен показывать требуемые человеко-часы для выбранного threshold.

Нельзя автоматически считать все FP обязательными ручными проверками, если конкретный операционный процесс заказчиком не утверждён. Это сценарная интерпретация, которую UI должен описывать явно.

## 14. CPU-ограничения

Заказчик отдельно ожидает работу на CPU.

Ориентиры:

- обучение одной модели — **не более 8 часов**;
- прогноз одной компании — **не более 2 минут**.

Для сравнения моделей фиксируются CPU train/inference time и, по мере реализации воспроизводимого замера, RAM/model size.

GPU не должен быть обязательным условием работы базового продукта.

## 15. Интерпретируемость

Объяснимость — обязательная часть оценки модели.

Для DS-моделей целевой формат включает:

- глобальную важность;
- локальные SHAP-значения/локальное объяснение;
- понятные top risk/top protective factors;
- связь explanation с конкретной версией модели и feature set.

Формулировки должны описывать **поведение модели**, а не причинность.

Запрещено писать «признак вызвал дефолт», если эксперимент показывает только ассоциацию/вклад в прогноз.

## 16. LLM

Текущее проектное решение:

- LLM **не является кредитной моделью**;
- LLM **не принимает решение** о дефолте;
- LLM используется как интерпретатор уже рассчитанных ML-результатов и объяснений.

LLM должна учитывать актуальные business rules и ограничения, чтобы не рекомендовать запрещённый feature set.

Вопрос о допустимой локальной LLM и использовании внешнего LLM API для обезличенных результатов остаётся открытым у заказчика.

До получения разрешения внешний API не считается обязательным компонентом автономной поставки.

## 17. Фокус интерфейса

Подтверждённый приоритет: **сравнение моделей, параметров и признаков**.

Рабочий интерфейс менеджера/карточка ИНН является следующей или опциональной частью относительно исследовательского тренажёра.

## 18. Расширение признаков

Заказчик планирует расширять набор факторов и приветствует новые, в том числе нестандартные и даже «безумные» гипотезы из внешних источников.

Новые признаки:

- не добавляются массово без гипотезы;
- должны быть доступны до момента прогноза;
- должны иметь понятный источник/provenance;
- сравниваются в контролируемом эксперименте;
- не обязаны сразу внедряться в production — допустим список обоснованных предложений.

Пример от заказчика для отдельной проверки: статус системообразующего предприятия. Его направление влияния нельзя считать доказанным без данных и эксперимента.

## 19. Переобучение

Ориентир заказчика:

- минимум — примерно раз в год;
- максимум — по сигналу обновления данных во внешнем источнике.

На текущем этапе это требование влияет на воспроизводимость и modular design, но не требует немедленно строить scheduler/monitoring stack.

## 20. Автоматизированная СПР

Долгосрочная цель заказчика — автоматизированная система принятия решений (СПР).

Следствие для текущей архитектуры:

- вероятность, threshold, business policy и explanation должны быть разделены;
- прогноз должен быть аудируемым;
- версия модели/feature set/config должна восстанавливаться;
- финальное автоматическое правило решения не утверждается исследователем без согласованной бизнес-политики.

## 21. Хранение истории

Ориентиры заказчика:

- данные для перемоделирования и история — около **3 лет**;
- история прогнозов вероятности дефолта — около **5 лет**.

Это будущие требования хранения и аудита, а не основание заранее вводить сложную production-инфраструктуру.

## 22. Final test

Final test используется только для финальной проверки заранее выбранного решения.

Запрещено использовать final test для выбора:

- модели;
- признаков;
- гиперпараметров;
- class weights;
- threshold;
- ранней остановки;
- нового feature engineering.

## 23. Открытые вопросы

1. Каково утверждённое отношение/стоимость FN и FP?
2. Какие локальные LLM разрешены/предпочтительны?
3. Разрешён ли внешний LLM API при передаче только обезличенных агрегированных результатов?
4. Что является седьмым внешним «100% default» событием, если формулировка «7 внешних» была намеренной?
5. Когда появятся данные с корректной датой наблюдения для временной проверки?
6. Как именно связать модельные ошибки/threshold-сценарии с бизнес-KPI ПДЗ `15% → 10%`, чтобы не придумывать эту связь исследователем?
