# Архитектура развития ветки `research/shap-llm-interpreter`

## Цель и границы

Разделить два сценария: исследование качества на размеченных исторических данных и применение сохранённой модели к новым строкам без метки. SHAP для исследования Stage 2 остаётся отдельным историческим обзором. Прогноз и локальный SHAP по ИНН относятся к конкретной версии обученной модели и конкретной строке входного файла.

Нынешний Streamlit — интерфейс локально запущенного Python-процесса. База данных для первого рабочего варианта не обязательна; версии моделей и их метаданные хранятся в игнорируемом Git каталоге приложения. При переносе в многопользовательскую среду понадобятся общее хранилище, права доступа и управление жизненным циклом артефактов.

История загруженных файлов в локальном прототипе хранится отдельно от версий моделей: файлы — в `.streamlit-artifacts/uploads/`, ограниченный реестр — в `.streamlit-artifacts/upload-history/`, версии — в `.streamlit-artifacts/models/`. Случайный идентификатор в URL позволяет восстановить только свою историю после перезагрузки страницы. Это не механизм аутентификации: ссылку нельзя передавать другим людям, а для сетевого многопользовательского развёртывания нужны учётные записи и разграничение доступа. Восстановление истории не означает восстановление подтверждённого датасета или текущего эксперимента; каталог моделей восстанавливается с диска независимо от истории браузера.

```text
Размеченный CSV/XLSX/XLSB
  → фактический просмотр структуры
  → подтверждение цели, класса события, ИНН, периода и ролей столбцов
  → подготовленный DatasetContract / FeatureRegistry / EvaluationPopulation
  → выбор разрешённых признаков и алгоритма
  → OOF-оценка без доступа к закрытому final test
  → отдельное обучение итоговой модели на разрешённой обучающей популяции
  → неизменяемая версия модели + метаданные + проверка целостности

Новый CSV/XLSX/XLSB с ИНН и признаками, без DefMark
  → выбор сохранённой версии модели
  → проверка схемы, типов, пропусков и идентификаторов
  → пакетный прогноз
  → поиск ИНН/периода → SHAP только для выбранной строки
  → позднее: LLM-пояснение только по проверенным фактам
```

## Владение компонентами

| Слой | Ответственность |
| --- | --- |
| `src/komus_risk/data`, `preparation` | Физическое чтение, факты о колонках, предложения ролей; предположения не становятся автоматически подтверждённым контрактом. |
| Будущий сервис подтверждения датасета | Явный выбор цели, положительного класса, идентификатора, периода, допустимых признаков и популяции; защита от утечки целевой информации. |
| `registries`, `planning`, `experiments`, `models` | Согласование выбранных признаков, алгоритма и протокола; оценка качества на размеченных данных. |
| `application/model_training.py` | Отдельное итоговое обучение строго после проверенного OOF-артефакта, только на разрешённой популяции; никакого обучения на новом файле для прогнозирования. |
| `artifacts/model_store.py`, `models/gbdt/native.py` | Раздельное файловое хранение отчётов об эксперименте и исполняемых версий моделей без pickle. |
| `application/model_inference.py` | Проверка CSV/XLSX/XLSB по точной схеме сохранённой модели и пакетный прогноз без переобучения. |
| Будущий сервис локального SHAP | Объяснение ровно той модели и той строки, для которых показан прогноз; вычисление по запросу. |
| `app/` | Компоновка сервисов, состояние мастера и представление в Streamlit; вычислительная ML-логика не дублируется в UI. |

## Идентичность обученной модели

Название алгоритма («XGBoost») — не идентификатор обученной модели. Версия должна связывать: хеш исходного обучающего датасета и подтверждённого контракта; цель и положительный класс; идентичность обучающей популяции; упорядоченный список имён, типов и семантики признаков; правила преобразования; версию алгоритма, параметры, seed и версию кода/библиотек. Разные датасеты или разные наборы признаков дают разные версии даже при одном алгоритме. Переобучение создаёт новую версию, старые версии не перезаписываются.

Для пользователя показывать понятное имя, например «XGBoost · Data_final · 47 признаков · 21.09.2026», и короткий технический ID. Имя можно менять; технический ID и манифест — нет. Экспериментальный артефакт с Gini сам по себе не является обученной моделью для новых строк. После успешной оценки нужен отдельный этап итогового обучения на разрешённой обучающей популяции; закрытый final test не используется для выбора или дообучения.

Реализованное локальное размещение: `.streamlit-artifacts/models/<model_version_id>/` с нативными файлами CatBoost `.cbm`, XGBoost `.json` или LightGBM `.txt` (для среднего ансамбля — все три), JSON-паспортом и SHA-256 файлов. Запись публикуется атомарным переименованием подготовленного каталога; сохранённый нативный файл проверяется пробной загрузкой до публикации. При загрузке проверяются целостность, версия кода и библиотек, связь с OOF-конфигурацией и порядок признаков. Версия имеет новый UUID даже при повторном обучении той же конфигурации; датасет, популяция, признаки и алгоритм связаны паспортом версии. Это контроль случайного повреждения, не криптографическая защита от злоумышленника с доступом к каталогу. Нельзя загружать непроверенные сериализованные Python-объекты из пользовательского файла. Каталог приложения не помещается в Git и требует резервного копирования, если версии надо сохранять надолго.

## Данные для прогноза и ошибки схемы

Новый файл не требует `DefMark`, но должен содержать ИНН и все признаки выбранной версии в согласованном представлении. Список признаков после обучения заблокирован. Лишние колонки не становятся признаками автоматически. Для отсутствующих признаков, повторных названий, несовместимых типов, NaN/Inf, повторных ИНН и неоднозначных периодов нужен явный результат проверки до прогноза. Правила допустимых пропусков зависят от сохранённой версии модели.

Для похожих, но не совпадающих имён (например латинская `A` и кириллическая `А`) показывать точное ожидаемое и найденное имя и предложение ручного сопоставления. Unicode NFKC сам по себе не делает эти буквы одинаковыми. Автоматическое молчаливое переименование запрещено; подтверждённое сопоставление записывается в протокол загрузки. Совпадение имени без совпадения смысла, единиц измерения и даты доступности показателя также недостаточно.

Пакетные прогнозы можно вычислить один раз для всего проверенного файла, хранить с ключом «версия модели + хеш входного файла + подтверждённая схема». Выбор одного ИНН не должен запускать обучение или пересчёт всего пакета. Если ИНН не уникален, строка выбирается по ИНН и периоду/идентификатору записи. SHAP вычисляется по запросу для выбранной строки и кешируется с тем же ключом и идентификатором строки. Прогноз — риск, а не известный факт дефолта; Gini для файла без меток не рассчитывается.

## Этапы реализации

1. **Просмотр физической структуры — реализован.** После проверки источника показываются реальные заголовки CSV/XLSX/XLSB без полной повторной загрузки. Это только факты; произвольный файл не становится готовым к ML.
2. **Подтверждение датасета — реализовано как отдельная подготовка.** По явному действию пользователя выполняются `TabularReader → DatasetInspector → DatasetPreparationAnalyzer`; факты и предложения показаны раздельно. Пользователь подтверждает цель, положительный класс, идентификатор и допустимые числовые признаки. Создаются DatasetContract, FeatureRegistry и EvaluationPopulation только для строк нового файла, без исторических индексов Stage 3. Подтверждённый контекст остаётся вне действующего пути эксперимента, а паспорт имеет статус `confirmed_pending_protocol`.
3. **Оценка конфигурации — реализована для нетемпоральных файлов с уникальным ИНН.** После подтверждения ролей пользователь отдельно подтверждает отсутствие временной оси. Датасет переводится в контекст исследовательской OOF-оценки; далее в обычных вкладках выбираются подмножество разрешённых признаков, алгоритм, seed и число фолдов. Цель, ИНН и предупреждённые proxy-поля не становятся признаками. Для выбора показывается стабильный ID конфигурации, результаты OOF сохраняются как артефакты эксперимента. При обнаружении возможных столбцов года/даты/периода активация блокируется: временной протокол ещё не реализован.
4. **Версия модели — реализована для поддерживаемых четырёх алгоритмов.** После успешной OOF-оценки пользователь явно запускает итоговое обучение на её разрешённой популяции: для исторического `Data_final` только working-часть, для нового подтверждённого датасета — все размеченные строки. Нативная модель и паспорт сохраняются отдельной неизменяемой версией; каталог виден на экране данных и после перезагрузки страницы. На экране результата сохранённая версия определяется по OOF-артефакту, датасету, алгоритму и набору признаков; после сохранения повторная кнопка для этого результата неактивна и предлагается вернуться в начало или открыть исторический SHAP Stage 2. Последний не является SHAP этой новой версии. При загрузке проверяются целостность, совместимость runtime и точная схема признаков. Прогноз нового файла без меток в этом этапе ещё не добавлен.
5. **Пакетное применение — базовый путь реализован.** Клик по строке каталога открывает экран версии модели с видимой таблицей всех признаков, выпадающим списком для просмотра отдельного описания и шаблоном CSV. Это ровно признаки сохранённой версии; менять набор признаков уже обученной модели нельзя. Дата создания в каталоге показывается как `дд.мм.гг` по московскому времени. Пользователь загружает CSV/XLSX/XLSB с ИНН и всеми значениями признаков; точные имена, уникальность ИНН и конечные числовые значения проверяются до прогноза. Похожие названия с буквами разных алфавитов подсказываются, но не подменяются автоматически: пользователь исправляет исходный файл. Вероятности после успешной проверки всего файла можно скачать. Результат пока хранится только в сессии, а индивидуального SHAP ещё нет.
6. **Локальный SHAP и LLM.** Поиск ИНН/периода, прогноз и SHAP выбранной строки; затем необязательное LLM-объяснение на основе проверенных значений, словаря признаков и ограничений. LLM не рассчитывает риск и не меняет решение модели.

Какие именно изменения сделаны в этапах 1–4, в каких файлах и чем они проверены, записано в соответствующих разделах документа [«Изменения ветки»](BRANCH_RESEARCH_SHAP_LLM_INTERPRETER_CHANGES.md).

После этапа 2 интерфейс показывает подтверждённую конфигурацию, но не запускает обучение до отдельного согласия на нетемпоральный OOF-протокол. На этапе 3 backend повторно проверяет идентичность исходного файла и не допускает файл с обнаруженными временными полями, повторяющимися ИНН, менее чем 60 строками или менее чем 30 наблюдениями каждого класса. Этот консервативный минимум учитывает дополнительное внутреннее разбиение бустинга на каждом OOF-фолде. Пользователь также явно подтверждает, что в данных нет скрытой временной последовательности: обнаружение имён столбцов не может заменить знание смысла данных.

Для нового файла OOF использует все его строки: каждая строка получает прогноз модели, не обучавшейся на этой строке. Результат — исследовательская метрика на размеченном наборе, **не** независимая финальная проверка и **не** версия модели для новых ИНН. Анализ ролей в этапе 2 уже видел весь файл, поэтому нельзя объявлять часть этих же строк «закрытым final test» задним числом. Чтобы оценивать прогноз на будущих периодах или несколько строк одного ИНН, нужны отдельный временной/групповой протокол и изменение текущих ограничений подготовки; случайная OOF-оценка для них запрещена.

Для `Data_final` из 362 018 строк заранее выделены 289 614 рабочих и 72 404 закрытых контрольных строк. OOF делит **только рабочие** строки на стратифицированные фолды (обычно 3): каждый рабочий ИНН проверяется моделью, не видевшей его при обучении соответствующего фолда. При подборе числа деревьев внутри каждого обучения делается дополнительное стратифицированное разделение 90/10 для early stopping, после чего модель переобучается на всей разрешённой обучающей части. Сохранённая итоговая модель обучается на всех 289 614 рабочих строках; закрытые 72 404 не участвуют ни в этом обучении, ни в OOF-метриках интерфейса. Для нового подтверждённого датасета OOF строится по всем его строкам, а итоговая модель затем также обучается на всех размеченных строках; независимого final test у него нет.

Выбрать несколько ИНН из рабочего датасета для будущей демонстрации индивидуального SHAP технически можно после реализации применения модели и этапа 6. Для сохранённой итоговой модели это будут уже **обучающие** строки, поэтому их объяснения не следует называть независимым тестом качества. Для проверки на невиденных примерах лучше использовать отдельно подготовленные строки с теми же признаками, не входившие в обучение; закрытый final test `Data_final` нельзя открывать ради подбора красивых примеров или настройки интерфейса.

Текущий экран Stage 2 SHAP остаётся историческим обзором и не подменяет этап 6. Этап 3 имеет указанную область применимости; этап 4 сохраняет модель, но не оценивает её на закрытом final test. Базовый пакетный прогноз этапа 5 уже доступен из каталога моделей; он не выполняет SHAP и не даёт оценки качества по файлу без истинных меток. Индивидуальный SHAP, LLM, постоянное хранение прогнозов и временное расширение этапа 3 пока не реализованы.

### Необязательный словарь смысла признаков

После подтверждения ролей нового датасета, но до OOF, пользователь может загрузить отдельный CSV/XLSX/XLSB-словарь с `column_name` и `description`. На экране прогноза словарь можно дополнить для уже сохранённой модели. Строки сопоставляются только с точными именами обучающих столбцов; неизвестные и повторные имена отклоняются, совпадение букв разных алфавитов предлагается только как подсказка. Неописанные признаки отображаются как «Описание не указано» красным, а не заменяются вымышленной бизнес-расшифровкой. Для принятого исторического датасета используются 17 подтверждённых смыслов из Stage 17; для остальных 30 подтверждения нет. Значения пользовательского словаря приоритетнее исторических и относятся только к точному отпечатку датасета.

Словарь хранится локально и версионируется отдельно от файлов модели в `.streamlit-artifacts/feature-descriptions/`. Это важно: `FeatureRegistry.registry_hash` сейчас включает `description_ru`, поэтому изменение старого `FeatureSpec` после OOF нарушило бы связь датасета, эксперимента и модели. Отдельный слой отображения не меняет веса, конфигурацию или паспорт сохранённой модели и не требует переобучения. Для будущего LLM-объяснения надо передавать статус происхождения описания и явный маркер отсутствия, не делать вывод о смысле по названию столбца.
