# Спецификация продукта

## Статус

Актуальная продуктовая основа исследовательского инструмента. Здесь фиксируется **что должен уметь продукт**, но не детали реализации конкретного модуля.

Неопределённые бизнес-параметры не додумываются и не зашиваются в код.

## 1. Назначение

`Komus Credit Risk` — исследовательская система для сравнения моделей прогнозирования дефолта, наборов признаков и бизнес-сценариев принятия решения.

Первичный пользователь — аналитик/DS, который должен уметь быстро и воспроизводимо проверить гипотезу и сравнить её с baseline.

Вторичный пользователь — нетехнический stakeholder/заказчик, которому нужен понятный интерфейс сравнения моделей, объяснений и бизнес-компромиссов.

Рабочий интерфейс кредитного менеджера и интеграция с продуктивными системами — последующее развитие, не первый приоритет.

## 2. Основной исследовательский сценарий

Пользователь должен иметь возможность:

1. выбрать модель;
2. выбрать существующий feature set;
3. включить/отключить отдельные допустимые признаки;
4. задать разрешённые гиперпараметры модели;
5. выбрать evaluation protocol из заранее определённых безопасных вариантов;
6. запустить эксперимент;
7. получить единый `ExperimentResult`;
8. сравнить результат с baseline и другими экспериментами;
9. сохранить конфигурацию и артефакты запуска.

Система не должна позволять незаметно менять target, split, seed, feature set или правила оценки.

## 3. Поддерживаемые классы моделей

### Обязательный baseline нового этапа

- CatBoost;
- XGBoost;
- LightGBM.

Они должны быть повторно сравнены после исключения `Q_B1_norm` и `Q_B2_norm`.

### Современные альтернативы

После нового baseline допускаются отдельные контролируемые исследования современных CPU-подходов, но не «зоопарк моделей».

Для каждого кандидата до реализации должно быть записано:

- что именно проверяется;
- почему подход имеет смысл на текущих табличных данных;
- чем он отличается от сильных GBDT baseline;
- насколько реалистичен CPU-запуск;
- как будет оцениваться объяснимость;
- какой эксперимент может подтвердить или опровергнуть гипотезу.

Актуальный shortlist формируется отдельным web research по первичным источникам непосредственно перед экспериментом.

## 4. Наборы признаков

Система должна поддерживать именованные `FeatureSet` и позволять сравнивать их при неизменном evaluation protocol.

Обязательные правила:

- в frozen historical Data_final profile `Q_B1_norm` и `Q_B2_norm` доступны только как reference/diagnostic signals;
- для historical рабочего кандидата оба признака запрещены;
- исторически заблокированные признаки не должны случайно возвращаться через пользовательскую конфигурацию этого profile;
- новые признаки добавляются модульно и исследуются отдельными гипотезами;
- provenance и доступность признака на момент прогноза должны быть понятны до включения в рабочий feature set.

## 5. Метрики качества

Каждый сопоставимый эксперимент должен возвращать как минимум:

- Gini;
- ROC-AUC;
- PR-AUC;
- Precision;
- Recall;
- F1;
- confusion matrix;
- FP и FN;
- Brier score/калибровочные показатели по мере интеграции общего evaluator.

В интерфейсе обязательно указывается уровень оценки: CV, OOF, validation, final test, bootstrap или другой stability check.

Метрики разных уровней нельзя показывать как равнозначные без явной маркировки.

## 6. CPU и ресурсы

CPU-практичность является частью продукта.

Для моделей по мере готовности общего runner фиксируются:

- время обучения на CPU;
- время инференса на CPU;
- доступное число потоков/ключевые параметры окружения;
- размер модели на диске;
- оценка RAM при обучении/загрузке, когда измерение реализовано воспроизводимо.

Ориентиры заказчика:

- обучение — не более 8 часов;
- прогноз одной компании — не более 2 минут.

Более высокое качество не считается автоматической победой, если прирост минимален, а стоимость по CPU/объяснимости существенно хуже.

## 7. Explainability

Система должна показывать не только вероятность дефолта, но и объяснение работы модели.

Минимально:

- глобальная важность;
- локальное объяснение выбранной компании;
- SHAP для поддерживаемых DS-моделей;
- top risk factors;
- top protective factors;
- версия модели и feature set, к которым относится объяснение.

Интерфейс должен явно сообщать, что SHAP/importance описывают поведение модели, а не доказывают причинность.

## 8. Threshold и бизнес-сценарий

Threshold не должен быть жёстко зашит в модель.

Пользователь должен иметь возможность:

- выбрать threshold вручную;
- посмотреть несколько стандартных сценариев;
- позже выбрать автоматический threshold по утверждённой бизнес-функции или ограничению.

Изменение threshold не требует переобучения модели.

## 9. Настраиваемая стоимость FN и FP

Стоимость ошибок — отдельный runtime-параметр бизнес-сценария, а не гиперпараметр ML-модели.

Frontend должен поддерживать два понятных режима.

### Режим A — реальные стоимости

Пользователь вводит:

- `C_FN` — стоимость пропущенного дефолта;
- `C_FP` — стоимость ложной тревоги/необоснованного ограничения хорошего клиента.

Система показывает условную/денежную стоимость ошибок для каждого threshold.

### Режим B — относительное соотношение

Если реальные суммы неизвестны, пользователь задаёт отношение:

`C_FN : C_FP`

Например, `5:1` означает, что один FN считается в пять раз дороже одного FP. Значения `5` и `1` не являются фиксированной политикой проекта.

Пока заказчик не подтвердил стоимость, результаты этого блока маркируются как **исследовательский сценарий**, а не «оптимальный бизнес-порог».

## 10. Ёмкость ручной проверки

Frontend должен иметь возможность учитывать ограничение на ручную проверку.

Будущие параметры:

- максимальное число компаний на ручную проверку за период;
- период: день/месяц/квартал или иной согласованный интервал;
- среднее время ручной проверки одной компании;
- число доступных аналитиков/человеко-часов при необходимости.

Текущий ориентир заказчика — около 30 минут на один ИНН. Конкретный лимит компаний не зашивается и должен быть настраиваемым.

Система должна уметь показать, как выбранный threshold влияет на:

- число компаний, отправляемых на проверку;
- Recall и Precision;
- FP/FN;
- ожидаемые человеко-часы.

## 11. Сравнение экспериментов

Пользователь должен видеть несколько экспериментов в едином формате и понимать, сопоставимы ли они.

Для каждого эксперимента отображаются:

- dataset identity/hash;
- feature set;
- модель и версия библиотеки;
- параметры;
- split/folds/seed;
- уровень метрик;
- threshold/business policy;
- CPU runtime;
- explainability status;
- дата/идентификатор запуска.

Интерфейс не должен автоматически ранжировать несопоставимые результаты как один leaderboard.

## 12. Артефакты и воспроизводимость

Значимый эксперимент должен сохранять достаточный набор для воспроизведения:

- config;
- dataset hash;
- feature schema;
- model parameters;
- metrics;
- predictions/OOF при необходимости;
- runtime;
- library versions;
- explanation artifacts;
- manifest/status;
- model artifact, если это оправдано.

Тяжёлые бинарные артефакты не обязаны находиться в Git.

## 13. LLM Result Interpreter

LLM является отдельным post-processing слоем.

Она должна получать только структурированные результаты, которые ей разрешены, и формировать понятный отчёт:

- что проверялось;
- что произошло;
- какие модели лидируют;
- как изменились метрики;
- какие ограничения остаются;
- что результат не доказывает;
- какой следующий вопрос логичен.

LLM не должна:

- менять рассчитанные метрики;
- выбирать запрещённый feature set вопреки business rules;
- самостоятельно принимать кредитное решение;
- подменять SHAP причинными формулировками;
- получать идентификаторы компаний через внешний API без отдельного разрешения.

Конкретный провайдер LLM не является частью контракта ML-core.

### Integration V1 — требования к интерпретации результата

Для selected-row сценария LLM получает только structured facts, производные от принятого `LocalExplanationEvidence`:

- identifier/row provenance;
- готовую probability;
- `shap_output_space`, raw model output и base value;
- top feature contributions с raw value / SHAP / rank;
- optional trusted feature descriptions.

LLM не должна:

- пересчитывать или менять probability;
- пересчитывать SHAP;
- утверждать причинность;
- придумывать бизнес-смысл признака без trusted description;
- выбирать threshold;
- выдавать решение «одобрить/отказать»;
- превращать отсутствие provider в отказ prediction/SHAP path.

Provider подключается через общий `ResultInterpreterClient`. Конкретная model/provider configuration не хардкодится в core/UI.

Для OpenAI adapter обязателен `store=False`; это не означает Zero Data Retention. Перед использованием внешнего provider на реальных клиентских identifiers/feature values должна быть отдельно подтверждена допустимая data-sharing/redaction policy.

## 14. Backend

Backend должен быть тонким слоем над тем же research/ML-core, который используется в notebooks.

Будущие операции:

- список доступных моделей;
- список feature sets;
- запуск experiment;
- получение статуса/результата;
- расчёт threshold/business scenario;
- получение explanation;
- сравнение экспериментов;
- позже prediction по компании/пакету компаний.

Backend не содержит собственной копии алгоритмов обучения или расчёта метрик.

## 15. Frontend

Первый frontend — исследовательский тренажёр, а не production CRM.

### Язык пользовательской части

Весь пользовательский интерфейс проекта оформляется на **русском языке**:

- кнопки, меню, сообщения, подсказки и статусы;
- подписи таблиц, графиков и метрик;
- названия экранов и пользовательских настроек;
- отчёты и пояснения результатов;
- Markdown-текст исследовательских notebooks.

Стандартные названия моделей, библиотек и общепринятые технические термины не переводятся искусственно.

В Python-коде допускаются английские имена функций, классов, переменных и внутренних backend/API-сущностей. Комментарии и docstrings оформляются на русском языке.

Основные экраны/блоки в перспективе:

- Модели и признаки;
- Настройки эксперимента;
- Метрики и сравнение;
- Порог и стоимость ошибок;
- Ёмкость ручной проверки;
- Объяснимость;
- LLM-сводка;
- Артефакты и воспроизводимость.

Ближайший defense-ready flow использует уже принятые application boundaries и не создаёт новый верхнеуровневый экран.

Верхнеуровневый путь остаётся:

`Данные → Признаки → Модель → Эксперимент → Результат`.

На `Результат` добавляется блок **«Применить модель к новым данным»**.

### III-C1 — локальное применение модели

`Результат → explicit save ModelVersion → targetless file → PredictionBatch → selected row → LocalExplanationEvidence`.

Требования:

- ModelVersion создаётся только явным действием пользователя;
- текущая сохранённая версия становится active для этого Result;
- targetless файл не проходит Dataset Preparation, его schema source — ModelVersion;
- prediction table строится из `PredictionBatch` и показывает dynamic identifier + probability;
- duplicate identifier values допустимы, выбор строки идёт по `row_id`;
- local explanation вызывается по capability; `UNSUPPORTED` не блокирует inference.

### III-C2 — внешняя интерпретация

`LocalExplanationEvidence → external-data policy/redaction → ResultInterpreter → provider adapter → explanation`.

Default: `EXTERNAL_DATA_POLICY=DISABLED`.

Defense-ready режим `REDACTED_V1` не передаёт внешнему provider:

- identifier value;
- raw feature values;
- row identity.

Provider/model/API key не хардкодятся в Streamlit и не сохраняются в model/experiment artifacts.

Frontend работает через `IntegrationWorkflowService` и capability contract; он не должен знать внутренности CatBoost/OpenAI и не должен содержать hardcoded `INN`, `DefMark`, feature names, provider model или threshold.

Главный UX invariant: отказ следующей capability не ломает уже успешные предыдущие результаты. LLM failure не очищает prediction/SHAP; unsupported local explanation не очищает PredictionBatch.

Красивый frontend не строится раньше устойчивого `ExperimentRunner`.

## 16. История и аудит

Архитектура должна позволять в будущем хранить:

- историю данных/перемоделирования около 3 лет;
- историю прогнозов около 5 лет;
- версию модели и параметров;
- explanation/audit trail для прогноза.

На текущем исследовательском этапе это требование не обязывает сразу вводить production-БД.

## 17. Не входит в ближайший scope

Пока не требуется:

- production-интеграция с 1С/CRM;
- высоконагруженная инфраструктура;
- Kubernetes/очереди/оркестрация;
- полноценная БД только «на будущее»;
- промышленный monitoring/drift stack;
- автоматическое кредитное решение без исследовательской валидации;
- переписывание исторического notebook №06 с нуля.

## Dataset Preparation V1

Для generic dataset система выполняет factual inspection и строит proposal.

Пользователь явно подтверждает:

- что модель должна предсказывать;
- какое значение является положительным событием;
- какой столбец идентифицирует объект;
- какие колонки использовать в модели;
- какие оставить только для анализа;
- какие не использовать.

Только после explicit confirmation dataset становится run-ready.

Historical `Data_final` является frozen compatibility profile и не задаёт правила generic product.

## Generic Dataset Onboarding UX

Основной пользовательский сценарий начинается с:

**«Загрузите файл»**

Пользователь не выбирает отдельный режим «исторический / новый датасет».

Onboarding строится как последовательный мастер:

`Файл → Цель → Идентификатор → Признаки → Оценка → Проверка`.

На экране одновременно активен один смысловой этап. Завершённый этап сворачивается в компактную строку и может быть открыт для изменения.

### Файл

После выбора файла необходимые технические проверки запускаются автоматически либо через понятное действие:

**«Проверить файл»**

Термин «Проверить источник» в основном UI не используется.

Показывается краткая сводка:

- имя файла;
- число строк;
- число колонок;
- число найденных проблем.

Повторяющиеся предупреждения агрегируются. Технические детали скрываются в разделе «Подробности».

### Цель

Главный вопрос:

**«Что модель должна предсказывать?»**

Analyzer может предложить кандидатов, но предложение системы не является подтверждением.

Target всегда явно выбирает человек.

После этого пользователь отвечает:

**«Какое значение считать положительным событием?»**

Варианты берутся только из фактических значений текущего target.

При смене target positive class сбрасывается.

### Идентификатор

Вопрос:

**«Какой столбец идентифицирует объект?»**

Подсказка объясняет, что это может быть ID клиента, ИНН, номер договора и т.п. Identifier не используется как predictor.

### Признаки

Для 50–200 колонок не показывается длинная последовательность больших dropdown.

Сначала выводится сводка:

- готовы к использованию;
- требуют решения;
- рекомендуется исключить.

Детальный список открывается при необходимости.

Пользовательские статусы:

- `MODEL_ALLOWED` → **Использовать в модели**;
- `DIAGNOSTIC_ONLY` → **Оставить только для анализа**;
- `BLOCKED` → **Не использовать**.

Внутренние статусы `FEATURE_CANDIDATE`, `TARGET_CANDIDATE`, `REVIEW_REQUIRED`, `ELIGIBLE_CANDIDATE` и аналогичные не показываются в основном UI.

### Оценка

Если V1 поддерживает только одну evaluation policy, фиктивный selector не создаётся.

Пользователь явно подтверждает:

**«Использовать все строки для OOF-оценки. Отдельная финальная тестовая выборка автоматически создана не будет.»**

### Проверка

Перед materialization показывается компактное summary:

- dataset;
- target;
- positive event;
- identifier;
- число predictors;
- число diagnostic-only;
- число excluded;
- evaluation setup.

Основные действия:

**«Изменить»**

**«Подтвердить и продолжить»**

## Dataset History / Persistence V1

Система должна позволять продолжать исследование после перезапуска приложения.

Exact dataset определяется по содержимому, а не по имени файла или пути.

Переименование или копирование идентичного файла не создаёт новую dataset identity.

Если exact dataset уже известен и сохранённое состояние совместимо с текущими правилами, приложение предлагает:

- **Продолжить работу**;
- **История экспериментов**;
- **Проверить заново**.

Повторный дорогой inspection не выполняется без необходимости, если совместимость сохранённого состояния доказана.

SHA-256, fingerprint, manifest, policy hash и cache не являются понятиями основного UI. Они доступны только в технических сведениях.

### Что сохраняется

Для dataset history нужны как минимум:

- dataset identity;
- последняя подтверждённая preparation;
- target и positive event;
- identifier;
- feature usage summary;
- версии relevant preparation/inspection rules;
- evaluation setup;
- список experiments;
- feature selection каждого experiment;
- model и parameters;
- Gini / ROC-AUC;
- PR-AUC;
- Recall;
- Precision;
- F1;
- runtime;
- reproducibility/provenance references.

### История экспериментов

Основной вид — таблица.

Пользователь может выбрать несколько экспериментов и увидеть их результаты рядом.

Прямой controlled comparison допустим только при одинаковых критичных experimental conditions: dataset identity и population, split/folds, seed, preprocessing, feature set, evaluation protocol и metrics — кроме заранее объявленного единственного changed dimension конкретного controlled experiment.

Если критичные условия различаются более чем по этому контролируемому изменению, результаты должны быть помечены как `partially comparable` или `incomparable`. Интерфейс не должен представлять их как прямой leaderboard или делать вывод о победителе на основании такого сравнения.

### Изменение правил

Exact dataset не означает, что старый analysis всегда остаётся актуальным.

Если relevant rules изменились:

- старая история сохраняется;
- experiment results сохраняются;
- старый inspection не выдаётся за актуальный;
- при необходимости предлагается обновить проверку.

### Similar dataset

Поиск похожих, но не идентичных dataset и перенос старых настроек не входят в V1.

В будущем такие настройки могут переноситься только как `PROPOSAL / DRAFT`, но не как автоматически подтверждённый `CONFIRMED` state.

Конкретное физическое хранилище пока не фиксируется. Это требование само по себе не является основанием вводить production-БД.
