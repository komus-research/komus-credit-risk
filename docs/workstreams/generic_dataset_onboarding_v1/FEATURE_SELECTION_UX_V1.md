# Feature Selection UX V1 — SPEC

## 1. Цель и граница этапа

Feature Selection UX V1 заменяет временный поштучный выбор признаков на
generic-интерфейс для датасетов с 50–200 колонками. Это детализация шага
«Признаки» из `SPEC.md`; она не меняет остальной Dataset Preparation flow.

Принятый порядок работы на экране:

`сводка → признаки, требующие внимания → поиск → фильтры → технические группы → массовые действия → решение по одной колонке → подтверждение`.

Интерфейс помогает найти и подтвердить решения пользователя. Он не создаёт
новых научных или бизнес-смыслов данных.

---

## 2. Источники данных и неизменяемые границы

### 2.1. Технические группы

Единственный canonical source generic-группировки —
`DatasetPreparationProposal.technical_groups`.

UX показывает группы, уже предложенные Analyzer, без их пересчёта, объединения
или дополнения. Допустимые `group_kind` и порядок их применения определяются
существующим proposal:

1. `structural_prefix`;
2. `repeated_token`;
3. `logical_type` как fallback;
4. `fallback`, если он присутствует в proposal.

`group_key` — технический ключ для поиска и подписи группы, например
`finance`. Такая подпись означает только совпадение в структуре имени колонки;
она не утверждает, что колонки относятся к предметной области «Финансы».

«Без группы» — presentation bucket, а не новая техническая группа. В него
входят:

- колонки существующей `fallback` technical group, если она есть;
- любые physical columns, которых нет ни в одной группе из
  `DatasetPreparationProposal.technical_groups`.

Второй случай необходим, поскольку Analyzer может не создать группу для
единственной оставшейся колонки. UI не вычисляет и не добавляет proposed
technical group: он только безопасно показывает такие колонки в presentation
bucket, чтобы ни одна physical column не исчезла из шага. Все physical columns
остаются доступны в отображении и включаются в полный пользовательский draft.

Нельзя создавать semantic/business groups («Финансы», «Платежи», «Клиенты»)
из внешнего знания, LLM или эвристик UI. Нельзя развивать отдельный generic
grouping engine в `app/feature_display.py`.

Группа — только средство навигации. Она:

- не меняет решение или `FeatureUsageStatus` колонки;
- не влияет на семантику `FeatureRegistry`;
- не делает запрещённую колонку доступной;
- не становится новым contract `FeatureGroup`;
- не входит в scientific semantics.

### 2.2. Решения и ограничения

Analyzer выдаёт proposal, а не подтверждённые роли. В UI существует
редактируемый пользовательский draft; он может содержать системное предложение
как начальное значение, но не является final confirmation.

Принцип состояния: `Analyzer proposal ≠ user draft ≠ final confirmation`.
Финальная валидация и materialization полного draft происходят только на шаге
«Проверка» через существующий `confirm_dataset_preparation`. Именно после него
создаётся тот же `PreparedDatasetContext`, что и без данного UX-слоя.

Backend остаётся authoritative source окончательной технической валидности
ролей. До final confirmation UI применяет только существующие UI-ограничения
ролей и не выводит их из названия группы, поисковой выдачи или локальных
эвристик.

TARGET и IDENTIFIER не могут одновременно стать predictors. BLOCKED —
пользовательское draft/confirmed решение, а не глобальный eligibility ban:
пользователь при возврате на шаг может изменить «Не используется» на
«Использовать в модели». Итоговый `MODEL_ALLOWED` всё равно проходит
существующую backend validation только при final confirmation. Группировка сама
по себе никогда не меняет статус колонки.

### 2.3. Состояние «требует внимания»

«Требует внимания» — пользовательская метка для колонок, по которым
существующий preparation flow ещё требует обязательного решения или не имеет
валидного draft-решения. Её состав берётся из существующих proposal/validation
данных; UI не вводит свой алгоритм риск-классификации.

Это состояние не является `FeatureUsageStatus` и не заменяет технические enum.
После корректного решения такая колонка исчезает из списка требующих внимания;
перемещение между группами, поиск и фильтрация на него не влияют.

## 3. Основной экран

### 3.1. Сводка

В верхней части экрана всегда показаны четыре счётчика по текущему
пользовательскому draft:

- «В модели»;
- «Только для анализа»;
- «Не используются»;
- «Требуют внимания».

Счётчики обновляются после успешного изменения draft. Они не являются
действиями и сами не изменяют фильтры или решения.

### 3.2. Признаки, требующие внимания

Сразу под сводкой показан компактный блок «Требуют внимания»:

- число unresolved признаков;
- короткий список или ссылка на них, если список длинный;
- понятная причина для каждой колонки;
- действие перейти к соответствующей строке/группе.

Этот блок существует до поиска и групп, чтобы обязательные вопросы не
терялись среди 50–200 колонок. Переход лишь меняет представление списка; он
не подтверждает и не меняет решение.

### 3.3. Поиск и фильтры

После блока внимания размещается панель управления списком:

- поиск по имени колонки;
- фильтр статуса: «В модели», «Только для анализа», «Не используются»,
  «Требуют внимания»;
- фильтр технической группы, в том числе «Все группы» и «Без группы»;
- текстовый показатель «Показано X из Y».

Все активные фильтры и поисковая строка работают через пересечение. Они
только меняют видимость строк и групп: не меняют draft, не меняют выделение и
не посылают решений в backend.

«Все группы» очищает только фильтр технической группы и возвращает полный
набор групп; остальные фильтры и поиск сохраняются. «Без группы» выбирает
presentation bucket: существующую `fallback` group и physical columns, которых
нет в `technical_groups`. Это не признак ошибки и не повод создавать новую
proposed technical group.

## 4. Групповой список

### 4.1. Accordion

Результат показывается accordion-блоками технических групп. В заголовке
каждой группы есть:

- стрелка раскрытия;
- пользовательская подпись технического ключа или «Без группы»;
- количество колонок в группе;
- сводка текущих решений: «N в модели · N только для анализа · N не
  используется»;
- маркер и число unresolved, если они есть.

Пример вида:

```text
▼ finance — 12 признаков
10 в модели · 1 только для анализа · 1 не используется

▶ payment — 8 признаков
▶ client — 17 признаков
▶ Без группы — 6 признаков
```

Количество и статусы в заголовке относятся ко всем колонкам группы, а не
только к текущим совпадениям поиска. При активном поиске/фильтрах UI отдельно
показывает количество совпадений в группе, чтобы не создавать ложного
впечатления, что остальные колонки исчезли или изменились.

### 4.2. Раскрытие при большом количестве колонок

Для 150–200 колонок обычные группы первоначально свёрнуты. Группы, содержащие
unresolved признаки, первоначально раскрыты.

При непустом поиске раскрыты только группы с совпадениями; группы без
совпадений не отображаются. После очистки поиска восстанавливается обычное
состояние раскрытия с обязательным раскрытием групп, в которых остаются
unresolved признаки.

Пользователь может работать с одной выбранной группой через фильтр группы,
не загружая весь список. «Все группы» всегда возвращает полный список.

### 4.3. Строка колонки

В раскрытой группе строка колонки показывает в человекочитаемом виде:

- имя колонки;
- системное предложение;
- текущее решение пользователя;
- короткую причину;
- действие «Почему? / Подробнее»;
- чекбокс, если колонка доступна для выбора.

Технические enum, включая `MODEL_ALLOWED`, `DIAGNOSTIC_ONLY`, `BLOCKED` и
`REVIEW_REQUIRED`, в основном UI не показываются. Детали по ссылке
«Почему? / Подробнее» объясняют решение человеческим языком и могут
раскрывать технические сведения только в отдельном подробном блоке.

Кнопка изменения одной колонки открывает её выбор допустимых решений. До
финального подтверждения набор ограничивается существующей UI-логикой ролей:
например, TARGET и IDENTIFIER не предлагаются как predictors. После явного
выбора UI обновляет пользовательский draft, эту строку, сводку и
соответствующий заголовок группы. Окончательная техническая валидность
проверяется существующим backend только при final confirmation.

## 5. Выделение и массовые действия

### 5.1. Выделение

Выделение предназначено только для явного последующего массового действия.
Выделенные строки сохраняются при раскрытии/сворачивании групп и фильтрации,
но фильтры сами не добавляют и не снимают выделение.

Внутри каждой раскрытой группы доступны действия:

- «Выбрать доступные»;
- «Снять выбор».

«Выбрать доступные» выбирает только видимые в этой группе колонки, для
которых соответствующее изменение допустимо по существующей UI-логике ролей.
Оно не меняет их решений.

### 5.2. Панель массовых действий

При наличии выделения появляется панель с действиями:

- «Использовать в модели»;
- «Только для анализа»;
- «Не использовать»;
- «Снять выделение».

Изменение выполняется исключительно после явного нажатия на одно из трёх
решений и является локальным редактированием пользовательского editable draft.
Для всех выбранных допустимых колонок UI обновляет текущие draft-решения
`column_statuses` и, если применимо, `blocked_reasons`.

При bulk action нет backend-вызова, per-column backend validation или
partial-success semantics. Если существующая UI-логика заранее знает, что
действие недопустимо для TARGET, IDENTIFIER или иной недоступной роли, оно не
предлагается для такой колонки и не включается в «Выбрать доступные».

Окончательная техническая валидность, включая допустимость итогового
`MODEL_ALLOWED`, остаётся за существующим backend и проверяется только при
final confirmation полного draft на шаге «Проверка».

## 6. Подтверждение признаков

Внизу шага находится единственное действие завершения этого шага:

**«Подтвердить признаки»**.

Пока существуют обязательные unresolved решения, кнопка disabled. Рядом
показана точная причина:

> Нужно принять решение ещё для N признаков.

Ни поиск, ни фильтр, ни раскрытие группы, ни массовое выделение не являются
подтверждением. Нажатие «Подтвердить признаки» сохраняет решения признаков в
editable UI draft, проверяет только, что обязательные решения этого шага
заполнены, и переводит пользователя на шаг «Оценка».

Это действие не создаёт `ConfirmedDatasetPreparation`, не materialize-ит
датасет и не создаёт `PreparedDatasetContext`. Полная последовательность
wizard остаётся такой:

`Файл → Цель → Идентификатор → Признаки → Оценка → Проверка → confirm_dataset_preparation → PreparedDatasetContext`.

Только на финальном шаге «Проверка» существующий
`confirm_dataset_preparation` выполняет final confirmation, backend validation
и materialization полного draft. При ошибке UI показывает понятное сообщение
о том, что нужно исправить, и возвращает пользователя к затронутым решениям.
Технические коды и traceback в основном UI не показываются.

## 7. Инварианты

1. Analyzer proposal ≠ user draft ≠ final confirmation.
2. Техническая группа не меняет статус признака.
3. Search, filters и groups сами ничего не изменяют.
4. Bulk action выполняется только после явного действия пользователя.
5. Backend — authoritative source допустимых ролей и финальной валидации.
6. `DatasetPreparationProposal.technical_groups` — единственный canonical
   source generic grouping.
7. Отдельный generic grouping engine в `app/feature_display.py` не создаётся
   и не развивается.
8. Historical `Data_final` UX не используется как основа generic flow.
9. Backend contracts и `PreparedDatasetContext` не меняются без отдельного
   архитектурного решения.
10. Semantic grouping не входит в этот этап.

---

## 8. Не входит в этап

- semantic/LLM grouping;
- ontology;
- новый Analyzer algorithm;
- изменение DatasetPreparation backend contracts;
- изменение FeatureRegistry semantics;
- History/Persistence;
- новые ML-модели;
- изменение evaluation protocol.

---

## 9. Acceptance criteria

Работа принимается, если:

1. 50–200 колонок не превращают экран в длинную простыню;
2. есть поиск по имени колонки;
3. есть фильтр статуса;
4. есть фильтр технической группы;
5. есть «Все группы» и «Без группы»;
6. группы сворачиваются;
7. проблемные группы автоматически раскрываются;
8. поиск раскрывает только группы с совпадениями;
9. есть bulk selection и bulk actions;
10. backend restrictions нельзя обойти через UI;
11. отдельную колонку можно изменить;
12. technical enums скрыты из основного UI;
13. unresolved признаки блокируют переход на шаг «Оценка»;
14. «Подтвердить признаки» сохраняет валидный draft и переводит только на
    шаг «Оценка», не создавая `ConfirmedDatasetPreparation` и
    `PreparedDatasetContext`;
15. final confirmation и materialization происходят только на шаге
    «Проверка» через существующий `confirm_dataset_preparation`;
16. после final confirmation существующий Dataset Preparation flow продолжает
    работать без изменения backend semantics.
