# ПРЕДЛОЖЕНИЕ

Сделать **«Подготовку нового набора данных» как короткий мастер внутри шага «Данные»**, а не как одну огромную таблицу из десятков колонок.

Путь:

**1. Выбрать файл → 2. Посмотреть, что найдено → 3. Подтвердить ключевые решения → 4. Проверить признаки → 5. Получить готовую конфигурацию подготовки.**

Главная идея интерфейса — на каждом шаге явно разделять:

**Найдено в файле** → факт
**Система предлагает** → гипотеза
**Вы подтвердили** → принятое решение

Критические решения — цель, значение целевого события, идентификатор, роль подозрительных колонок — никогда не должны подтверждаться автоматически.

---

# ПОЧЕМУ

Такой flow понятен человеку без Data Science, потому что ему не предлагают сначала разбираться в `dtype`, cardinality и leakage score.

Система сначала говорит простым языком:

> «Файл прочитан. В нём 362 018 строк и 51 колонка.»

Потом:

> «Мы предполагаем, что `DefMark` — целевая колонка. Вот почему.»

И только затем спрашивает:

> «Подтвердить или выбрать другую?»

То есть пользователь **проверяет готовые предположения**, а не проводит EDA самостоятельно.

При этом scientific validity сохраняется: система помогает принять решение, но не выдаёт эвристику за установленный факт.

# 1. ПОШАГОВЫЙ ПУТЬ ПОЛЬЗОВАТЕЛЯ

## Шаг 1. Выбор файла

Пользователь видит:

> **Подготовка нового набора данных**
> Выберите файл. Система изучит его структуру и предложит первоначальную настройку.

Основное действие:

**[ Выбрать файл… ]**

После выбора:

> **client_data.xlsx**
> Анализируем структуру файла…

На этом этапе пользователь ничего про признаки не настраивает.

---

## Шаг 2. Результат чтения файла

После успешного чтения сначала показывается **только факт**:

> ✓ **Файл успешно прочитан**
>
> `client_data.xlsx`
>
> **362 018** строк
> **51** колонка
>
> Найдены числовые, текстовые и другие типы данных.
> Есть 4 колонки, которые требуют внимания.

Основное действие:

**[ Посмотреть предложения системы → ]**

Вторично:

**[ Выбрать другой файл ]**

Здесь не нужно сразу показывать таблицу из 51 колонки.

---

## Шаг 3. Ключевые решения

Сначала три критических вопроса:

1. **Что нужно прогнозировать?**
2. **Какое значение означает интересующее событие?**
3. **Какая колонка идентифицирует объект?**

Только после их разрешения пользователь переходит к признакам.

---

## Шаг 4. Проверка признаков

Система показывает подготовленную классификацию:

* предлагается использовать как признак;
* предлагается исключить;
* требует проверки;
* служебная/идентификационная колонка;
* целевая колонка.

Затем — первоначальная группировка.

---

## Шаг 5. Итог перед подтверждением

Короткое резюме:

> **Настройка набора данных**
>
> Цель прогноза: `DefMark` ✓
> Интересующее событие: `1` ✓
> Идентификатор: `INN` ✓
> Для модели выбрано: 47 признаков
> Исключено: 4 колонки
> Требуют внимания: 0
>
> **[ Подтвердить подготовку ]**

Если остаются обязательные нерешённые вопросы, кнопка disabled с конкретной причиной.

# 3. БЛОКИ

## Блок «Файл»

### Пользователь видит

Название файла, успешность чтения, строки, колонки и количество обнаруженных проблем.

Например:

> ✓ **Файл успешно прочитан**
>
> `companies_2026.xlsx`
>
> 72 404 строки · 53 колонки
>
> ⚠ 3 колонки требуют внимания

### Может изменить

Только выбранный файл.

### Подтверждает

Ничего. Размер и структура файла — **факты**, а не решение пользователя.

### Предупреждения

Ошибки чтения, неизвестный формат, неоднозначные настройки чтения.

---

# Блок «Цель прогноза»

Здесь особенно важно показать разницу между фактом и предположением.

### Wireframe

```text
Цель прогноза

СИСТЕМА ПРЕДЛАГАЕТ

DefMark                                  Уверенность: высокая

Почему мы предлагаем эту колонку:
• найдены два значения;
• пропусков нет;
• название похоже на целевой показатель.

[ Подтвердить DefMark ]   [ Выбрать другую колонку ]

Подробнее ▾
```

После подтверждения:

```text
Цель прогноза

✓ ПОДТВЕРЖДЕНО

DefMark

[ Изменить ]
```

### Пользователь может изменить

Выбрать другую колонку из доступных кандидатов.

### Пользователь подтверждает

Именно **роль колонки как целевой**.

Не её тип и не статистику.

---

# Блок «Интересующее событие»

Этот вопрос нельзя объединять с выбором target.

Если `DefMark` содержит `0` и `1`, UI должен прямо сказать:

> **В колонке `DefMark` найдены значения `0` и `1`.**
>
> Система не может надёжно определить, какое из них означает интересующее событие.
>
> **Какое значение считать событием, которое модель должна выявлять?**

Controls:

```text
○ 0
○ 1
```

Если backend действительно имеет предложение, его можно отметить:

> **Система предполагает: `1`**
> Требуется ваше подтверждение.

Но система **не имеет права предвыбрать radio так, чтобы пользователь мог случайно проскочить шаг**.

После выбора:

> ✓ **Подтверждено: интересующее событие — `1`**

Я бы здесь вообще не использовала термин **«положительный класс»** на основном уровне.

В `Подробнее` допустимо:

> Технический термин: positive class.

---

# Блок «Идентификатор»

### Wireframe

```text
Идентификатор объекта

СИСТЕМА ПРЕДЛАГАЕТ

INN                                      Уверенность: высокая

Почему:
• значения почти не повторяются;
• пропусков нет;
• название похоже на идентификатор.

Идентификатор используется для различения объектов
и не рассматривается как обычный признак модели.

[ Подтвердить INN ]    [ Выбрать другой ]
```

Это последнее предложение допустимо только если оно соответствует уже принятой backend/application semantics. Если backend лишь предлагает роль, а исключение из predictors происходит после подтверждения, UI не должен обещать больше.

### Несколько кандидатов

Если есть `INN`, `CompanyID`, `RowID`:

> **Нужно выбрать идентификатор**
>
> Найдено несколько подходящих колонок.

Карточки:

```text
○ INN
  Почти все значения уникальны · пропусков нет
  Система считает этот вариант наиболее вероятным.

○ CompanyID
  Все значения уникальны · пропусков нет

○ RowID
  Все значения уникальны
  ⚠ Название похоже на номер строки.
```

Основное действие:

**[ Подтвердить выбранный идентификатор ]**

---

# Блок «Признаки»

Не показывать пользователю 50 колонок одной плоской технической таблицей.

Сначала summary:

> **Потенциальные признаки**
>
> Предлагается использовать: **47**
> Требуют проверки: **3**
> Предлагается исключить: **4**

Затем группы.

```text
Префикс Q_A                                      6 из 7

☑ Q_A1_norm
☑ Q_A4_norm
☑ Q_A5_norm
...
⚠ Q_A7_result       Требует проверки

────────────────────────────────

Числовые                                         12 из 13
...

Прочее / не определено                           5 из 6
...
```

Если backend способен предложить группу только по префиксу — именно так её и называем.

Никаких выдуманных:

> «Финансовая устойчивость»

если такого смысла в evidence/backend нет.

---

# Блок каждой колонки

Для обычного состояния:

```text
☑ G1_norm

Числовой показатель
Пропуски: нет

Предлагаемая роль: признак модели

Почему:
значения меняются между строками,
явных технических признаков не обнаружено.

Подробнее ▾
```

В `Подробнее` уже можно показывать:

* технический тип;
* логический тип;
* число уникальных;
* долю уникальных;
* безопасные примеры;
* служебные диагностические признаки.

# 4. ОСОБЫЕ СОСТОЯНИЯ

## Успешная загрузка

Не надо писать:

> `INSPECTION_READY`

Пользователь видит:

> ✓ **Файл успешно прочитан**
>
> Найдено 72 404 строки и 53 колонки.
>
> Система изучила структуру файла и может предложить первоначальную настройку.

**[ Посмотреть предложения → ]**

---

# Неоднозначная цель

Например backend вернул три подходящих кандидата.

```text
⚠ Нужно уточнить цель прогноза

Мы нашли несколько колонок, которые могут быть целевыми.
Выберите ту, результат которой должна прогнозировать модель.

○ DefMark
  Два значения · без пропусков
  Уверенность системы: высокая

○ DefaultFlag
  Два значения · 2,1% пропусков
  Уверенность системы: средняя

○ Status
  Четыре значения
  Уверенность системы: низкая

[ Подтвердить выбранную цель ]
```

Нельзя изображать самый высокий confidence как **«правильный выбор»**.

---

# Несколько идентификаторов

Не ошибка.

Статус:

> **Нужно выбрать идентификатор**

Система может написать:

> Мы нашли несколько колонок, которые похожи на идентификатор объекта.

Далее кандидаты + reasons.

Пользователь подтверждает один вариант либо выбирает предусмотренное backend значение «идентификатора нет», **только если такая semantics разрешена backend**.

---

# Подозрительный признак

Очень важно не писать «утечка обнаружена» как доказанный факт.

Карточка:

> ⚠ **Требует проверки**
>
> `DefaultResult`
>
> Эта колонка подозрительно тесно связана с предполагаемой целью.
>
> **Почему система обратила внимание:**
> связь с целевой колонкой необычно сильная.
>
> Проверьте, когда появляется это значение: до момента прогноза или после него.

Controls должны соответствовать разрешённым backend role decisions, например:

**[ Оставить как признак ] [ Исключить ]**

Если пользователь оставляет такую колонку, предупреждение не должно молча исчезать. Решение становится:

> ✓ Решение пользователя: оставить как признак
> ⚠ Предупреждение системы сохранено.

Это хороший пример различия **факта / предложения / подтверждения**.

---

# Недостаточно данных

`INSUFFICIENT_DATA` не надо переводить как «Недостаточно данных» без объяснения — это слишком абстрактно.

Лучше:

> ⚠ **Система не смогла предложить настройку автоматически**
>
> Файл успешно прочитан, но его структуры недостаточно, чтобы уверенно определить цель, идентификатор или роли колонок.
>
> Вы можете выбрать основные поля вручную.

Дальше показываем только те ручные действия, которые backend действительно поддерживает.

Если подготовку нельзя завершить вообще:

> **Подготовку этого файла сейчас нельзя продолжить.**

И объяснить конкретную причину из backend.

---

# Ошибка файла

`FILE_ERROR`:

> **Не удалось прочитать файл**
>
> `client_data.xlsx`
>
> {безопасное понятное объяснение backend}
>
> **[ Выбрать другой файл ]**
>
> Подробности ошибки ▾

Нельзя показывать в основном UI stack trace, exception class или сырой parser error.

---

# 5. ВИЗУАЛЬНЫЙ ЯЗЫК СОСТОЯНИЙ

Цвета могут помогать, но **никогда не должны быть единственным различием**.

| Смысл                          | Как показываем                            | Пример                      |
| ------------------------------ | ----------------------------------------- | --------------------------- |
| **Факт**                       | нейтральный блок + `НАЙДЕНО`              | `НАЙДЕНО · 72 404 строки`   |
| **Предложение системы**        | отдельная карточка + `СИСТЕМА ПРЕДЛАГАЕТ` | `DefMark`                   |
| **Подтверждено пользователем** | ✓ + `ПОДТВЕРЖДЕНО`                        | `✓ Цель: DefMark`           |
| **Предупреждение**             | ⚠ + `ТРЕБУЕТ ПРОВЕРКИ`                    | возможная утечка            |
| **Блокирующая ошибка**         | явный error-block                         | `Не удалось прочитать файл` |

Особенно важно: **«Высокая уверенность» никогда визуально не равна «Подтверждено»**.

Например:

> Система предлагает · высокая уверенность

остаётся предположением, пока пользователь не нажал **«Подтвердить»**.

---

# 6. ЧТО СПРЯТАТЬ ПОД «ПОДРОБНЕЕ»

Основной экран должен отвечать на два вопроса:

> «Что система нашла?»
> «Что мне сейчас нужно решить?»

Под **«Подробнее»** можно убрать:

* физический/технический `dtype`;
* точное количество уникальных значений;
* `unique_ratio`;
* внутренний confidence score;
* heuristic/diagnostic score;
* raw warning codes;
* настройки чтения файла;
* идентификатор версии файла;
* fingerprint/hash;
* backend role code;
* внутренние названия состояний;
* технические причины parser detection;
* полный список sample values, если основной UI показывает достаточно информации.

При необходимости:

> **Уникальных значений: 99,8%**
> *(доля строк с уникальным значением)*

а не:

> `unique_ratio: 0.998`.

# 7. ЧТО ЕЩЁ НУЖНО ОТ BACKEND ДЛЯ ЭТОГО UX

По описанию **данных для отображения почти достаточно**. Но для законченного UX-контракта координатору нужно подтвердить наличие следующих операций — это не новая backend-архитектура, а необходимые действия интерфейса.

### A. Подтверждение / изменение предложений

UI должен уметь передать backend подтверждённые пользователем:

* target column;
* значение интересующего события;
* identifier;
* role каждой изменённой колонки;
* inclusion/exclusion признака;
* подтверждённую группировку, если она входит в V1.

### B. Проверка итогового выбора

Перед **«Подтвердить подготовку»** нужен ответ backend:

* какие обязательные решения ещё не приняты;
* какие предупреждения остаются;
* есть ли блокирующая несовместимость.

UI не должен сам вычислять scientific validity.

### C. Альтернативы

Для target и identifier недостаточно только «лучшего кандидата». Нужен список допустимых альтернатив с теми же explanation/confidence, если backend его уже формирует.

### D. Человеческое объяснение blocking state

Для `FILE_ERROR` / `INSUFFICIENT_DATA` нужен безопасный `user-facing reason`, чтобы frontend не переводил exception самостоятельно.

### E. Статус предупреждения после user override

Нужно понимать, может ли пользователь сознательно оставить подозрительную колонку, и если да — какой backend state означает:

> «решение подтверждено, предупреждение сохранено».

Это особенно важно для leakage-warning UX.

### F. Момент формирования готового Dataset Preparation context

Нужно подтвердить одно: какое backend-событие означает, что все обязательные решения приняты и интерфейс вправе считать onboarding завершённым.

Я **не определяю это событие со стороны UX**.

# 8. V1 / V2 / V3

## V1 — обязательно

V1 должна закрыть весь безопасный happy path:

* выбор нового файла;
* состояние анализа;
* summary строк/колонок;
* `FILE_ERROR`;
* предложение target;
* ручной выбор target из кандидатов;
* обязательный выбор значения интересующего события;
* предложение identifier;
* выбор identifier;
* summary потенциальных признаков;
* предупреждения по отдельным колонкам;
* первоначальная группировка от backend;
* явные состояния **Найдено / Система предлагает / Подтверждено / Требует проверки**;
* подтверждение обязательных решений;
* блокировка завершения при unresolved required decisions;
* итоговое резюме подготовки.

Без этого Dataset Preparation не является полноценным пользовательским flow.

---

## V2 — удобство работы с большим числом колонок

Можно добавить:

* поиск по колонкам;
* фильтры `Все / Использовать / Исключить / Требуют внимания`;
* массовый выбор;
* сворачивание групп;
* изменение названия группы пользователем;
* более удобное сравнение нескольких target/ID candidates;
* сохранение незавершённой настройки, если application semantics это позволит.

---

## V3 — продвинутый UX

Не нужен для первого usable flow:

* визуальные распределения значений;
* мини-гистограммы;
* продвинутый data profiling;
* сравнение вариантов подготовки;
* история пользовательских изменений;
* дополнительные explanation-визуализации;
* автоматические рекомендации на основе предыдущих onboarding-сессий.

V1 не надо превращать в аналог Data Wrangler.

---

# UX HANDOFF FOR COORDINATOR

Для frontend впоследствии понадобятся следующие пользовательские компоненты:

1. **Dataset Preparation stepper**
   `Файл → Основные поля → Признаки → Проверка`.

2. **File inspection summary**
   имя файла, статус чтения, строки, колонки, количество предупреждений.

3. **Proposal Card**
   универсальная карточка вида:
   `Система предлагает → значение → уверенность → почему → Подтвердить / Изменить`.

4. **Target Selector**
   выбор целевой колонки из backend candidates.

5. **Event Value Selector**
   отдельный обязательный выбор значения интересующего события.

6. **Identifier Selector**
   предложение + альтернативы + объяснение.

7. **Feature Review**
   группы колонок, role/status, включение/исключение, warnings.

8. **Warning Card**
   нейтральная формулировка риска без утверждения недоказанного факта.

9. **Confirmed Decision state**
   отдельное визуальное состояние после пользовательского подтверждения.

10. **Preparation Summary**
    цель, событие, ID, количество используемых/исключённых признаков, unresolved warnings.

11. **Blocking / insufficient / file-error states**
    с понятным следующим действием.

12. **Technical disclosure — «Подробнее»**
    dtype, ratios, diagnostics, internal metadata и другие сведения, не нужные в основном happy path.
